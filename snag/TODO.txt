snag — known gaps / deferred work

Same spirit as scratchy/TODO.txt: things found-and-deliberately-deferred,
not a speculative feature backlog. See NOTES.md for the fuller story.

- [ ] A `style="..."` attribute's own CSS value isn't scanned for
      `url(...)` references (e.g. `style="background-image:
      url(foo.png)"` would keep a relative, now-broken URL in the
      bundle). Only `<style>` elements and `<link rel=stylesheet>` go
      through `process_css`. Real inline `style=` attributes are
      overwhelmingly plain property:value pairs in practice (confirmed
      on the Wikipedia test run — this didn't come up), so not worth the
      extra plumbing until a real page actually needs it.

- [ ] `srcset` isn't touched at all (PROMPTS.md v5: it's just another
      non-fetching attribute now, passed through with whatever relative
      URLs it already had) — scratchy has no responsive-image-candidate
      selection (or any `<img>` painting at all yet), so there's nothing
      to pick a candidate *for* or resolve a URL on its behalf. Revisit
      once scratchy actually renders images.

- [ ] No retry/backoff on a failed sub-resource fetch — one attempt,
      then fall back to the original (now-probably-broken) URL and move
      on. A flaky connection could silently drop resources that a retry
      would've recovered. Hasn't mattered in practice yet.

- [ ] No size cap or concurrency — every sub-resource is still fetched
      serially, one at a time, with no limit on how many. Measured
      directly (PROMPTS.md v7, `SNAG_TIMING=1`) on the Wikipedia test
      page: 244 requests, ~21ms average, no individual outlier —
      sequential latency alone accounts for ~89% of total wall time (5.2
      of 5.9s). Concurrent fetching is the obvious next lever if a
      slower network makes this feel like a stall rather than just
      "takes a few seconds" (every request measured here was fast; a
      network with meaningfully higher per-request latency would turn
      that same serial pattern into something that reads as actually
      hung) — not attempted yet, since it hasn't been needed on the
      networks this has actually been tested from.

- [ ] The CSS `url()`/`@import` rewriter is a hand-rolled text scanner
      (see NOTES.md's own design-choices section for why), not a real
      CSS tokenizer — a comment or string literal containing the
      literal text `url(` or `@import` could be misdetected. Not hit on
      real-world CSS tested so far (including Wikipedia's own). Each
      stylesheet's own *text* is still read in full before being scanned
      (needed to look ahead for a matching `)`/`;`) — PROMPTS.md v6
      removed the deeper buffering this used to have (every `url()`'s
      *referenced resource* used to be fully built as a base64 string,
      then the *entire* rewritten stylesheet written out in one piece;
      now each resource streams straight to stdout the moment it's
      resolved, same as `<img src>` always did).

- [ ] `@font-face` `src: url(...)` references get inlined as data URIs
      like any other CSS url, but scratchy has no `@font-face` support
      to ever use one — harmless dead weight in the bundle today, not
      worth skipping specially until scratchy can load a declared font.

- [ ] No `--base <url>` override flag for stdin mode when a page has
      neither `<base href>` nor `<link rel=canonical>` in its `<head>`
      — `discover_base` just warns and continues with no base, so any
      tag needing one falls back to passing its relative URL through
      unresolved (PROMPTS.md v5). Every real page tested so far (English
      and German Wikipedia) has emitted a canonical link, so this hasn't
      actually blocked anything; revisit if a real page without either
      shows up.

- [ ] `replace_src_with_placeholder` only rewrites a **quoted**
      `src="..."`/`src='...'` attribute — an unquoted `src=foo.png` is
      recognized fine when just *reading* the value (`parse_attrs`
      handles both forms), but isn't rewritten in place, so the tag
      passes through with its original (broken) relative src instead of
      being inlined. Real/machine-generated markup, including every page
      tested so far, always quotes its attributes; a narrow, accepted
      gap rather than something worth a more general splice-by-span
      rewriter for right now.

- [ ] `decode_entities` only covers the 5 predefined XML entities
      (`&amp;` `&lt;` `&gt;` `&quot;` `&apos;`) plus numeric character
      references (`&#NN;`/`&#xHH;`), not the full HTML5 named-entity
      table (`&nbsp;` and ~2000 others). The only place a decoded value
      is actually *used* is resolving a URL to fetch, and `&amp;` in a
      query string is by far the dominant real-world case there
      (confirmed constantly on Wikipedia's own `href`s) — anything else
      passes through literally rather than failing to decode, which
      would only matter if a URL itself contained an exotic named
      entity (not observed).

- [ ] `<title>`/`<textarea>` aren't treated as raw-text elements the way
      `<style>`/`<script>` are (PROMPTS.md v5) — in the vanishingly rare
      case either contains a literal `<`/`>` that isn't a real tag,
      the scanner could misread it. Not hit on any real page tested;
      `<style>`/`<script>` were the two that actually mattered (CSS/JS
      routinely contain `<`/`>`, title text essentially never does).

- [ ] `<![CDATA[...]]>` sections (an XML-ism, essentially never seen in
      real HTML) have no special handling the way `<!-- comments -->`
      do — a literal `>` inside one would end the "tag" early. Not hit
      on any real page tested.

- [ ] `<script defer>` reordering (PROMPTS.md v8) holds each deferred
      script's full raw bytes (tag + content + closing tag) in memory
      until `</body>` — bounded per script (not the whole document, see
      NOTES.md), but a page with an unusually large *inline* `<script
      defer>` block would still hold that one block's bytes the whole
      time. Not hit on any real page tested (every `defer` script seen
      so far has an external `src`, nothing inline of any real size).

- [x] **`snag --serve`: a long-lived local daemon mode, to support
      scratchy link navigation (v9, commit 186ef77).** `snag --serve`
      binds a Unix domain socket at `$XDG_RUNTIME_DIR/snag.sock`
      (falling back to `/tmp/snag-$UID.sock` when `$XDG_RUNTIME_DIR`
      is unset) and serves connections one at a time, forever. Protocol:
      a client writes one absolute URL + a newline, the server streams
      back exactly the bytes the one-shot `snag <url>` CLI would have
      printed for that URL, then closes the connection (close = EOF =
      done, mirroring the CLI's own process-exit today). Reuses the
      one-shot mode's exact fetch+inline logic via a new shared
      `bundle_url` function — not a second copy of it. No caching across
      requests (every request still does the full independent work the
      CLI already does — see the new deferred item below for what this
      explicitly leaves out). No concurrency — sequential, matching this
      file's already-serial per-resource fetch model. Started manually
      (`snag --serve &`); scratchy does not auto-spawn it. The existing
      one-shot `snag <url>`/stdin CLI modes are unchanged in shape;
      `--serve` is additive. Usage text updated to document it.

      Also landed in the same change, independent of `--serve` itself:
      `snag` now emits a real `<base href="...">` tag right after
      `<head>` opens, in BOTH `--serve` and the one-shot CLI mode —
      using whatever base value already resolved that page's own
      resource references (the fetched URL itself in `snag <url>`/
      `--serve` mode, or `discover_base`'s discovered value in stdin
      mode) — *unless* the real page already declares its own
      `<base href>`, in which case that one is left alone and nothing
      is injected. `discover_base` changed to always scan through to
      `</head>` (not stop at the first match) so a `<base>` tag
      appearing after a `<link rel=canonical>` in the source is still
      noticed for this check. First automated tests this project has
      ever had (`#[cfg(test)] mod tests` in `main.rs`, matching
      `scratchy/src/lib.rs`'s established in-file convention): 5 tests
      covering `<base href>` emission/non-duplication/omission and a
      real `--serve` round-trip over an actual Unix socket against a
      local HTTP fixture, diffed against calling `bundle_url` directly.
      Verified by hand too: installed, ran `snag --serve &`, hit it with
      a throwaway Python Unix-socket client (no `socat`/`nc`/`ncat`
      available here) for `https://example.com`, diffed against a plain
      `snag https://example.com` run — byte-for-byte identical, both
      carrying the new `<base href>`; served a second request on the
      same running process to confirm persistence; re-ran the real
      German Wikipedia pipeline through the plain CLI to confirm it's
      unaffected beyond the new tag.

- [ ] No caching across `--serve` requests (v9, explicitly deferred, not
      an oversight) — every request does the same independent full
      fetch+inline work the one-shot CLI already does, even for a URL
      requested moments ago through the same connection to the same
      site. Only worth adding if repeated-navigation latency on the same
      site (once scratchy's own click-navigation lands and this actually
      gets exercised interactively) turns out to matter in practice —
      not attempted speculatively.
