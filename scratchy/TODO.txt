DECISION (user, 2026-11-18): scratchy moves from QuickJS (rquickjs 0.14) to V8 (the `v8`
crate, i.e. rusty_v8, maintained by Deno). Reason: the most popular sites (YouTube,
DuckDuckGo) are unusable; their single callbacks need 0.5-1.7 s of QuickJS CPU (R36, R37),
and QuickJS is an interpreter with no JIT. This supersedes the 2026-11-14 engine note
("V8 ruled out: its speed solves a problem scratchy doesn't have", Tier 7 detail) and the
2026-11-15 "Go with rquickjs" choice. The user also wants before/after numbers, so the
migration starts and ends with the same measurement (QV8-0, QV8-m).

      QM1k-PLAN (Opus, 2026-11-18; evidence R34 + the "QM1k plan" addendum under it; user
      decisions = QUESTIONS.md Q4, all answered 2026-11-18):
      USER DECISIONS: (1) ~60 s of YouTube is the first milestone, PoToken later (QM1k2);
      (2) mp4 first (avc1/avc3 + mp4a, fragmented mp4), design CODEC-AGNOSTIC: mpv demuxes and
      decodes, scratchy never parses codecs or samples (it reads only container box headers for
      timing, see Q7); WebM/Opus/VP9/AV1 = a table flip + a WebM box reader later (QM1k1h/i);

      the early test QM1k-AB fails; (4) 64 MiB of appended media per player, tunable;

      than MSE (chain QWK0-QWK6 below, after QM1k-m2).
      ARCHITECTURE (one paragraph per layer; names are proposals, implementers may rename):
      - `src/mse_store.rs` (pure Rust, no JS, no mpv): per SourceBuffer a byte-stream reader
        behind a trait (`ByteStreamFormat`: feed bytes -> Init(bytes) | Media(bytes, t0, t1) |
        Error), first impl fMP4 (top-level boxes split across appends; ftyp+moov = init;
        styp/sidx/emsg/prft/moof+mdat = media; timescale from moov/trak/mdia/mdhd, start from
        traf/tfdt, length from trun sample durations or tfhd/trex defaults), and a segment store
        sorted by start time (segment granularity: an overlapping append replaces whole
        segments; `buffered` = merged segment ranges with a 0.1 s gap tolerance; `remove(a,b)`
        drops segments fully inside [a,b]; byte accounting for the cap).
      - Shared state `MseFeed` = Arc<Mutex<..>> + Condvar per MediaSource: the JS thread
        appends (never waits on mpv), mpv's demux threads read. A GENERATION = one mpv load:
        a start time and the contiguous run of segments from the one covering it; its bytes
        are init + those segments in time order (a virtual, growing file per track). New
        segments that continue the run are appended to the live generation; others are only
        stored (used by the next generation). A new init segment (quality switch,
        changeType) or a seek outside the live generation = a NEW generation (a reload with
        `start=<t>`, ~0.3-0.5 s, R30 open timings; measured in QM1k-AB).
      - mpv: a second stream_cb protocol `scratchy-mse://<feed>/<gen>/<v|a>` (D4 holds: the
        bytes came from page fetches through wire; mpv still gets no network URL). read_fn
        blocks on the Condvar until bytes, endOfStream (then 0 = EOF), cancel or unload;
        seek_fn within the generation's still-held bytes; size_fn unsupported (growing).
        Load: `loadfile scratchy-mse://F/G/v replace -1 start=<t>,rebase-start-time=no,
        demuxer-max-bytes=16MiB,demuxer-max-back-bytes=8MiB` with the audio stream added as an
        external track (mpv 0.41 here: `audio-files` is a PATH LIST split on ':' and the URL
        has one, so set it with `change-list audio-files append <url>` / a NODE array, and
        clear it before every load; or `audio-add <url> select` after file-loaded; QM1k1b
        picks the one that works and tests it). One SourceBuffer (muxed, or audio-only) = one
        stream, no external track. The load is issued only when every SourceBuffer has its
        init segment (mpv opens external tracks synchronously; a missing audio init would block
        it).
      - Element: `MediaBackend::load_mse(feed, start)` (default: Err "MSE not supported"; Fake
        and Mpv implement it); `MediaCore` gets an MSE attachment: duration = MediaSource
        duration (mpv's DurationChanged ignored), buffered = intersection of the active
        SourceBuffers' buffered, seekable = [0, duration], `progress` (350 ms throttle) on
        appends, `ended` only after endOfStream, seek inside the live generation = mpv seek,
        outside = `waiting` until both tracks cover t, then a new generation.
      - JS: a new `mse_prelude.js` (evaluated after media_prelude.js; zero cost until the
        first `new MediaSource`, QY6 rule) + natives in js_media.rs registered with
        `js_engine::native!`; bytes cross with `js_engine::Bytes`, which takes a `Uint8Array`
        ONLY (V8 backend: `v8::Uint8Array`, copy honours the view offset), so the prelude
        normalises ArrayBuffer / DataView / other views to `new Uint8Array(buf, off, len)`.

   entries still die only if something else calls attachShadow at module
   level (none measured), so most of github's JS runs anyway. chromestatus
   stays blank, MDN/salesforce keep today's (DSD-less) rendering.
B) Lightweight composed tree, in two stages.
   B1 "real DOM, not rendered": attachShadow returns a real ShadowRoot
   node (a DocumentFragment-kind node registered on its host in a Rust
   side table), with the JS API (host, mode, shadowRoot getter for open,
   innerHTML, querySelector scoped to the shadow tree, getRootNode,
   isConnected through the host, custom-element callbacks inside it,
   events climbing from shadow root to host). Rendering ignores shadow
   roots: the host's LIGHT children render exactly as today, and a
   one-time log line says shadow content is not rendered. Cost: M (QSD3)
   + S (QSD2). Gain: github relative-time/tool-tip run (measured), Lit
   apps (chromestatus, MDN) stop throwing; nothing new on screen.
   Risk: a component that hides its light children and shows only shadow
   content shows the light children (same as today when it throws).
   B2 "flattened rendering": layout/paint walk a composed tree:
   `composed_children(h)` = the shadow root's children if `h` hosts one,
   a `<slot>`'s assigned light nodes (by `slot=` name, default slot gets
   the rest, fallback content if none) if `h` is a slot in a shadow tree,
   else `h.children`. `<slot>` is a `display:contents` box, so
   `slot[name=x]{display:none}` hides its slotted nodes (MDN's dropdown
   does exactly that). Style: rules from `<style>`/`<link>`/adopted
   sheets inside a shadow root match only that tree (+ `:host`,
   `:host()`, `::slotted()` via the selectors crate hooks); document
   rules do not match into shadow trees; inheritance follows the
   composed tree (free: the layout walk passes `inherited` down).
   Hit-test/hover/focus-within use the composed parent; events retarget
   at the shadow boundary. Cost: display:contents (QSD5, M) + composed
   walk (QSD6, M) + scoping (QSD7, M) + retargeting (QSD8, S) + DSD
   (QSD9, M) ~ 4-5 M items. Gain: MDN's DSD widgets + salesforce's nav
   render; chromestatus can render once fetch works; github's
   relative-time renders through its shadow root (same text).

   nested slot re-distribution, `::part`/`exportparts`, `:host-context`,
   closed-mode leak proofing, `delegatesFocus` + sequential focus

[AUDIT 2026-11-16: points 5, 7 and 8 below are the pre-answer defaults.
The USER ANSWERS block further down overrides them and is what was
built: all methods with bodies (QF13), private/file targets warn and

Recommended design (fits the engine as it is: JS on the main thread,
App owns everything else, wire does the network):
1. JS side, a new `src/fetch_prelude.js`: spec-faithful data classes
   (Headers, Request, Response, Blob, File, FormData, TextEncoder/
   TextDecoder, a minimal ReadableStream), plus `fetch` and
   `XMLHttpRequest`, both thin layers over ONE native request queue.
2. Native `__net_send(...)` checks the request policy in Rust right
   away (a blocked request rejects at once with a clear log line) and
   records it in `JsRequests.net` (the QB5 request pattern). The engine
   never does I/O.
3. `App::js_sync` drains the queue and runs each request on its own
   thread (like image fetches, max 6 at a time per page). The result
   comes back as `AppEvent::JsNet(nav_generation, id, result)`.
   `JsEngine::deliver_net` resolves the promise or fires the XHR events,
   then drains promise jobs and runs `js_sync`. Stale generations are
   dropped, so a late response never reaches the next page.
4. Bodies are buffered (cap 16 MiB per response, 30 s timeout).
   `response.body` is a ReadableStream that delivers the whole body as
   one chunk. That is legal, and youtube feature-tests `getReader`
   anyway. Real streaming waits for a measured need (QF18).
5. Policy (enforced twice): scratchy refuses non-http(s) targets
   (`file:` always), non-GET/HEAD methods, mixed content and
   private/loopback/link-local hosts by name. wire refuses to CONNECT to
   a non-public address for requests marked `X-Wire-Policy:
   public-only`, at DNS resolution time, so redirects and DNS rebinding
   cannot get around it.
6. CORS like a browser for reads: same-origin is free. Cross-origin is
   readable only with a matching `Access-Control-Allow-Origin`, and only
   simple requests (no preflight until QF13). `no-cors` requests are
   answered with an opaque response WITHOUT being sent (the page cannot
   read an opaque response, so it cannot tell the difference).
7. No credentials of any kind: no cookie jar, `credentials` is
   accepted and ignored, `Cookie` and other forbidden request headers
   are dropped, `Set-Cookie` is hidden from JS. Nothing is persisted.
8. XHR events and readyState follow the spec order. Sync XHR throws
   `NetworkError`. `sendBeacon` returns true and sends nothing.
   `WebSocket`, `EventSource` and `Worker` stay ABSENT, so pages take
   their own fallback path.
9. `--js-report` performs the requests too (synchronously, through
   wire), prints a `--- network ---` section, and uses the copy's
   `<base href>` as the page URL. Today it uses the file:// URL, so
   origin checks would be wrong: guardian's beacon carried
   `url=file:///tmp/...`.

What was measured (build `0735ddd`): YouTube plus 9 other pages
(github, reddit, old.reddit, bbc news, duckduckgo, lobste.rs, guardian,
en.wikipedia, HN), `--js-report` and live windows with JS on and off,
and for YouTube an iterative chain of JS stand-ins until the app script
ran clean.

Key facts:
- YouTube no longer ships a custom-elements polyfill
  (`webcomponents-sd.js` = ShadyDOM + ShadyCSS only) and forces ShadyDOM
  (`ShadyDOM={force:true,noPatch:true}`), so it needs a native
  `customElements` and `template.content`, but NOT native Shadow DOM.
  No page in the survey uses declarative shadow DOM either. Native
  Shadow DOM + slots in the cascade/layout (the expensive part) has no
  measured user today.
- With 16 APIs supplied by JS shims (customElements and template.content
  with real semantics, the rest stubs), YouTube's 9.8 MB app runs to the
  end, upgrades ~100 custom elements and stamps a 1600-element app shell
  in the DOM, then starts 337 `fetch`es (1 API call, 336 icon SVGs). On
  screen nothing changes: the live window is the same grey skeleton as
  `--no-js`. No browse grid, no consent dialog in 20 s simulated.
  Next walls: fetch (Q33f, L), a real MutationObserver, quadratic DOM
  walking (QY8), then unknown (layout of the stamped DOM never reached).
- Across the other pages the most common blockers are NOT Web
  Components: ES modules (4 pages: github runs zero scripts, lobste.rs,
  guardian islands, old.reddit), `URL`/`URLSearchParams` (2 erroring,
  4 more use it), `matchMedia` (2), reflected `src` (2), `Intl` (kills
  duckduckgo's React app), `fetch` (2 erroring, everyone uses it). Visible
  CSS damage: `transform:translate` off-canvas drawers shown open
  (duckduckgo, bbc), `@layer` blocks dropped (github shows `hidden`
  banners), `<meta http-equiv=refresh>` missing (duckduckgo `--no-js`
  is blank).

Options:
A) Skip Web Components / YouTube for now. Cost 0. We lose: YouTube
   stays the grey skeleton (= what Chrome shows without JS); old.reddit's
   login form stays missing. We lose nothing else measurable today:
   github's custom elements are behind ES modules anyway.
B) Minimal stubs only (MutationObserver that never fires, AbortController,
   MessageChannel, SVGElement hierarchy, Window, HTML*Element objects,
   IntersectionObserver that says "visible", etc.). Measured: YouTube
   gets past startup ONLY if customElements and template.content are
   real; with them it builds its shell in the DOM and still shows
   nothing new. Stubs that never fire are also a trap: ShadyDOM and
   Polymer trust MutationObserver, so a silent stub turns into wrong
   rendering later instead of a clear error. Cost: about 10 S items.
   Payoff on YouTube: none visible.
C) Real implementations, ordered by measured payoff across sites
   (YouTube last). Phase 1 = cheap, correct, broad (QY8-QY14, all S).
   Phase 2 = the big enablers (QY15 ES modules M, Q33f fetch L, QY16 Intl
   M) plus four CSS fixes (QY17-QY20, S each; QY18 = translate-only
   `transform`, which the 2026-11-14 re-plan deliberately did not queue,
   so the user must OK it here). Phase 3 = Web Components for YouTube
   (QY6a MutationObserver M, QY6e customElements M, QY6f template.content
   M, QY6d re-measure), only if the user still wants YouTube after
   Phase 2. Even then YouTube content is not promised: the
   measurement stopped at fetch.

      - [ ] QY-IO-GEOMETRY [L] (2026-11-16: first slice split out as QJ4,
        then QJ5/QJ6/QJ7; QJ4 replaces the "stale cache" read below with a
        forced synchronous layout, see why there) the geometry bridge. Today JS cannot see
        layout: `getBoundingClientRect/getClientRects`, `offsetWidth/Height/
        Left/Top/Parent`, `clientWidth/Height`, `scrollWidth/Height`,
        `scrollTop` and the window's real size/scroll (Q33b2) do not exist
        or return 0, so IO/RO cannot be real. Design: after each layout
        (App's layout generation, the same place paint reads the layout
        tree) the app walks the laid-out boxes and publishes
        `Vec<(node_id, Rect)>` (border box in document coordinates, plus
        content box) plus viewport size and scroll offset into the engine
        (a shared `Rc<RefCell<GeometryCache>>` stamped with the layout
        generation; the JS thread/engine reads it, never `App`). JS getters
        read the cache (stale after DOM writes until the next layout:
        document it; a write that needs fresh geometry marks it dirty and
        returns the last known numbers). IO then recomputes intersections
        per generation and on scroll against the cached rects (threshold
        crossing, rootMargin, explicit roots with overflow clipping), RO
        compares content/border boxes per generation, both delivered as
        ordinary timer-0 callbacks after the layout event; observers with
        no targets cost nothing, and a page that never calls these never
        pays. Sizing: ~1 day for the cache + Rust publish +
        getBoundingClientRect/offsetWidth family; ~1 day for real IO/RO on
        top; hard part is the JS->App wake-up after a layout (callbacks
        run only when the event loop turns) and iframes/transforms (cut).
        NOT built here: the cache alone is small, but it needs the
        layout-generation hook in app.rs that the Q33g/Q33b2 work owns.

QSTASH — persistent web storage (user design session 2026-11-19; full design in STASH.md)
========================================================================

- QSTASH-D DESIGN (user, 2026-11-19; PROPOSED, DECIDED when the PR adding STASH.md
  merges; the items below follow STASH.md, not this summary): NO stash daemon. The
  filesystem is the backend interface: `--state-dir DIR` (default
  $XDG_STATE_HOME/scratchy, mode 0700; tmpfs = in-memory across scratchy restarts).
  localStorage = one FILE PER KEY under storage/<site>/<origin>/ (site schemeful as
  net_policy::site_of, `://` -> `!`; origin `scheme!host!port`); value = WTF-8 + one
  `\n`, reading strips one trailing `\n`; dotfiles and `*~` ignored; hand edits
  supported. Load once before the first script, no IO while JS runs, ops batched per
  task to a writer thread (temp file + fsync + rename / unlink). flock per site on
  storage/.locks/<site> (outside the data, never deleted; holds a generation number
  bumped by forget-site). No storage mutex, no cross-window storage events (same as
  browsers). sessionStorage never on disk. wire keeps the jar, gains --cookie-file.
  History: not now (waits for a reader). Supersedes QF-D7 for these stores.

- [ ] QSTASH1 [M] (P2, after the perf queue) `src/stash.rs`: the state directory and
      its rules, no JS wiring. Layout, key<->filename encoding (percent-encode `/`, `%`,
      NUL, a leading `.`, a trailing `~`; empty key `%`; >200 bytes -> `%h<sha256>` with

        standard proxy "absolute-form" request line (`GET https://
        example.com/path HTTP/1.1`, RFC 7230 §5.3.2) rather than the
        origin-relative form a direct browser connection would send —
        this is what lets a daemon behind a bare unix socket (no DNS/
        TLS-SNI of its own to infer a destination from) know exactly
        where to actually connect, using only standard HTTP syntax, no
        invented command/framing layer on top.

        resolved in conversation**: the daemon does *not* relay raw
        bytes 1:1 (that would leave chunked-decoding/redirect-looping/
        gzip-decoding as new HTTP-client logic inside scratchy, which
        contradicts "scratchy still doesn't do its own networking").
        It also doesn't try to collapse different content kinds into
        one shape — a fetched `index.html` and a fetched `photo.jpg`
        are genuinely different things scratchy must handle
        differently. The resolved contract: the daemon returns a clean,
        already-decoded HTTP/1.1 response — real headers, redirects
        already followed, body already decompressed, `Content-Length`
        never `Transfer-Encoding: chunked` — and scratchy reads exactly
        one header out of it to decide what the body *is*:
        `Content-Type`. `text/html` → the existing HTML-parse path
        (`new_parser().read_from(...)`, same as v65's `AppEvent::
        NavResult` success branch already uses). `image/png`/`jpeg`/
        `gif`/`webp` → the existing `decode_image_bytes` path (already
        built and tested for `data:` URI images — reusable verbatim on
        real fetched bytes, no new image-decoding code). Anything else,
        for now: a clear "can't render this content type" inline
        message, never an attempt to force unknown bytes through either
        path. Every other header (`Cache-Control`, `Server`, cookies,
        etc.) is read by nobody and simply discarded — confirmed with
        the user directly: normalizing the *transport* mess is the
        daemon's job, but deciding what the bytes mean stays scratchy's.

        multiplexing there — but concurrent *separate* connections are
        expected, not excluded.** Same dead-simple shape `snag --serve`'s
        own protocol already has: connect, write the request, read
        until the daemon closes, done, no request IDs or shared-
        connection framing. Discussed and settled in conversation: real
        multiplexing (interleaving several requests' bytes over one
        shared connection) would need both sides to agree on framing —
        it can't be hidden in the daemon alone, since scratchy is the
        other half of that exchange and would need new ID-tagging/demux
        code regardless of how smart the daemon is — and it would buy
        nothing here anyway, since a unix socket is local IPC with no
        handshake; opening several concurrent one-shot connections
        (future per-resource fetches firing off N background threads,
        the same shape `start_navigation`'s background thread already
        uses, just invoked more than once at a time) costs about as much
        as opening one. The real place for connection pooling/reuse is
        the *daemon's own upstream leg*, talking to real remote servers
        over actual TCP/TLS — the daemon is free to reuse/pool its own
        connections to the same remote host across multiple client
        requests however it likes, entirely invisible to scratchy, with
        zero protocol impact on the scratchy-facing socket. That's where
        the real performance cost (handshakes, round trips to a real
        server) actually lives, and it's already implied by "the daemon
        owns networking" — nothing new to design there, just a reminder
        not to conflate the two legs.
      - **`--socket <path>` becomes an explicit opt-in CLI flag**,
        replacing today's fixed-path auto-discovery entirely. No flag
        given, or any connection failure against the given path: falls
        all the way through to printing the raw request text to stdout
        (the literal HTTP/1.1 wire text — request line, `Host`, other
        headers, blank line, body — chosen specifically so it's directly
        replayable by `nc`/a raw socket/this same new daemon run
        manually, with zero translation) plus the existing inline
        "not available" status-message precedent (v65's connection-
        refused handling) — scratchy never gets a response back in this
        branch, by design; that's the whole point of the fallback.
      - **Forms and link-clicks become the exact same code path**: both
        reduce to "build a request (GET for a link or a `method=get`
        form, GET/POST for a form depending on its own `method`
        attribute), try the socket, else print" — resolving the
        asymmetry this conversation flagged earlier (link-nav always
        navigated live, forms always only printed; now both depend
        purely on whether `--socket` is active and reachable, not on

        dependency; resolve `action` against `base_url` via the existing

        earlier draft — only the transport underneath it changed.
      - **Click-side rewrite this item actually requires**:
        `build_box_for_element` needs the same early-

      - **Still just a transport, not a solution to async resource
