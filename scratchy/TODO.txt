scratchy — known gaps / deferred work

Plain checklist of things found-and-deliberately-deferred during work on
this project, so they don't get forgotten between sessions. Not a
feature backlog of things nobody asked for — only things we actually
hit and chose not to fix immediately. See NOTES.md for the fuller story
behind any item; a commit hash in parens points at the commit it came
up during (`git show <hash>`) — more precise than a PROMPTS.md version
number, since several versions can share one commit and a hash is
directly actionable. PROMPTS.md is append-only and never edited for
these.

- [x] `%` lengths (v49): `width`/`height` and their `min-`/`max-` forms,
      `margin`/`padding` (all four sides, including top/bottom — real
      CSS resolves a margin/padding `%` against the containing block's
      *width* on every side), `border-radius` (against this box's own
      border-box width), `font-size` (against the parent's font-size,
      same timing as `em`), and `line-height` (against the declaring
      element's own font-size) all now accept `%`. `width`/margin/
      padding/`border-radius` resolve against a containing-block
      dimension that isn't known until layout (`measure`, not
      `resolve_style`) — see `BoxLength`'s own docs for the deferred-
      resolution mechanism this needed. `height`/`min-height`/
      `max-height` follow the real spec rule for an indefinite
      containing block height (an ordinary `height: auto` ancestor):
      the percentage computes to `auto`, i.e. has no effect at all,
      exactly as if it weren't declared — not resolved against some
      made-up basis. `border-width`/`outline-width`/`box-shadow`'s
      offsets/blur/spread deliberately still reject `%` — the real CSS
      grammar for all of them is `<length>`, not `<length-percentage>`,
      so accepting a percentage there would be adding something the
      spec itself doesn't allow, not closing a gap.

      Unitless numbers (besides literal `0`) were also checked per this
      item's original wording: still correctly rejected everywhere
      except `line-height` (already valid pre-v49 — a bare `<number>`
      is that property's own real grammar, the single most common
      real-world form) — confirmed by grep and a permanent test, not
      changed, since real CSS doesn't allow a unitless non-zero number
      for any other property scratchy supports (`z-index`/`flex`/etc.,
      where it would be valid, aren't implemented at all).

      - [ ] No viewport/initial-containing-block height concept exists
            (v49) — unlike a real UA, whose initial containing block
            always has the window's own definite height, this engine's
            document-root box (a synthetic wrapper `<html>` is laid out
            *inside*, not literally the tree's root) has no height of
            its own, so the classic `html, body { height: 100% }`
            full-height pattern doesn't resolve to anything (same as
            not declaring it) — only an ordinary nested `%` height
            against an *explicit* ancestor height works. Tried wiring
            the window's own inner height through as the top-level
            `measure` call's `containing_height`, and reverted it: that
            value is also reused as the "total scrollable content
            height" `redraw`'s own scroll-clamping reads directly off
            the root `Laid`'s `h` — pinning it to the window's height
            would silently cap every page at exactly one viewport's
            worth of scrollable content, a real regression to actual
            scrolling, not a hypothetical one. Needs the root box's
            "containing-block-height" role and its "total content
            height for scrolling" role separated before this can be
            revisited, not a one-line fix.

- [x] Table layout (53bab7a) now does real CSS2.1 §17.5.2.2
      automatic table layout: each column's width is sized from the
      min/max content width of its own cells (`cell_natural_width`,
      distributed across the table's own content width by the real
      spec three-case rule — grow to fill if every column's max-content
      width fits, shrink proportionally if even every column's
      min-content width doesn't, interpolate between min and max
      otherwise), not the old equal-width-column split. One deliberate
      divergence from the literal spec, kept from before this item
      landed: a real auto-width table shrink-wraps to its own content;
      this one still stretches to fill its container (an auto `Blocks`
      box's existing behavior) — changing that is a separate, bigger
      scope than "size the columns from their content."

      Still out of scope, unchanged from before this item: no
      colspan/rowspan (default.css/real-world markup don't need them
      for anything scratchy renders yet), no border-collapse/borders-
      between-cells (default.css doesn't declare any table/cell
      borders), no `caption-side` placement (caption always renders in
      source position, which is first — same as the default anyway).
      One narrower gap newly surfaced by real column sizing: an
      explicit `width`/`min-width`/`max-width` set directly on a
      `<td>`/`<th>`, or a `<col width>`/CSS `width` on a `col`/
      `colgroup`, isn't honored as a column-sizing hint — only a cell's
      own *content* drives its column's width.

- [x] `font-family` (PROMPTS.md v16, named families/fallback lists:
      v51) now parses a real comma-separated fallback list — a quoted
      string (`"Georgia"`), an unquoted multi-word name joined with
      spaces (`Helvetica Neue`), and any of the 5 bare generic keywords,
      in any mix and order. Resolution against the real font system
      (not just the cascade) tries each named family in order and falls
      back to the next — or the trailing generic — exactly the way real
      CSS `font-family` fallback works: `fontdb::Database::query`
      already implements this in-order "first family with any installed
      face wins" search internally (confirmed by reading its vendored
      source, not assumed), queried one candidate at a time since
      `cosmic_text::Attrs::family` itself can only ever hold one
      resolved `Family`, not a list. Verified past the cascade: a
      permanent test shapes a list naming an impossible family before a
      real `monospace` keyword and confirms the shaped `cosmic_text::
      Buffer` actually lands on monospace's own `fontdb::ID`, not
      cosmic-text's default sans-serif. Also visually confirmed with a
      real `grim` screenshot against an installed named family
      (`Liberation Serif`) and both fallback cases.

      One architectural note worth flagging for a similar future
      property: `FontFamily` had to become a leaked `&'static` slice
      (`Box::leak`, once per distinct parsed declaration) rather than an
      owned `Vec`, specifically so `ComputedStyle`/`InheritedStyle`/
      `SpanStyle` could keep their existing `#[derive(Clone, Copy)]` —
      see PROMPTS.md v51 and NOTES.md v34's own note on this exact
      tradeoff for the full reasoning. Not a correctness gap, just a
      memory-reclamation one: a distinct `font-family` declaration's
      parsed list is never freed for the life of the process (bounded by
      how many distinct declarations a document's CSS has, not by
      element/redraw count — see PROMPTS.md v51 for why this was judged
      an acceptable, not a new-category, cost).

- [x] `text-decoration` (PROMPTS.md v17) originally only tracked the line
      keywords (underline/line-through/overline/none) — `dashed`/`dotted`/
      `double`/`color` now paint correctly too (PROMPTS.md v33, confirmed
      still true by grepping `parse_text_decoration`/`DecorationStyle` in
      `src/lib.rs` during the 2026-10-29 autonomous TODO.txt pass — this
      item was already fully resolved, just never checked off). See the
      `text-decoration-style`/`-color` item below for what's still open
      (that's a narrower, separate gap, not this one).
      `abbr[title] { text-decoration: dotted underline }` in default.css
      now actually renders dotted, not a plain solid underline.

- [ ] `<title>` has no `display: none` in `default.css` — confirmed by
      grep, there's no `head`/`title`/`meta`/`link`/`base` rule at all
      right now. Every real UA's default stylesheet hides the whole
      `<head>` subtree (and `title` specifically, since it's metadata
      content, not meant to render in the document body) via
      `display: none`. Right now scratchy likely renders the page
      `<title>`'s text visibly inline at the top of the document,
      which is wrong. Add it (and check whether `head`/`meta`/`link`/
      `base` need the same rule, or whether `head` already doesn't
      render for some other reason — verify before assuming).

The rest of this file is a full html-rendering feature-gap survey done
after v20 (commit 7950fc2), not individual things hit mid-feature like
the items above — see the conversation that asked "what features are
missing in regards to rendering html?" Grouped by area so a future
session can pick a coherent slice rather than one property at a time.

- [x] `position: relative`/`absolute`/`fixed` (PENDING_COMMIT_HASH) now
      work: `relative` offsets a box's painted position (`top`/`right`/
      `bottom`/`left`, px/`%`/`em`/`rem`) without affecting normal flow
      at all (siblings land exactly where they would if it had no
      offset); `absolute`/`fixed` are genuinely taken out of flow (no
      space reserved for them by their own parent) and positioned
      against the padding box of the nearest ancestor whose own
      `position` isn't `static` (`absolute`) or the viewport
      (`fixed`, immune to scroll — an orphaned `absolute` with no
      positioned ancestor anywhere above it uses the same viewport-
      sized rect, approximating the real CSS initial containing block).
      `z-index` (plain integer, `auto`/unset treated as `0`) controls
      paint/hit-test order *among boxes that share the same containing
      block* — out-of-flow descendants always paint after their
      containing block's own normal content, ascending by `z-index`,
      ties in document order. Real CSS §9.7's "computed `display`"
      rule is applied too: an `absolute`/`fixed` element's `display`
      always computes to `block` (unless it's `none`), so e.g. a
      `<span style="position: absolute">` gets its own box instead of
      being flattened into the surrounding inline run. 7 new permanent
      tests cover: relative offset leaving sibling flow untouched;
      relative `%` offset resolving against the containing block;
      absolute removed from flow + anchored to a positioned ancestor's
      padding box; absolute solving `right`/`bottom` from its own
      measured size; an orphaned absolute and a `fixed` box both
      bubbling to the document root (same containing-block rect,
      different scroll behavior); fixed staying anchored to the
      viewport regardless of a 3000px-tall preceding sibling; and a
      real painted-pixel check that a higher-`z-index` box wins an
      overlap despite appearing earlier in document order.

      **Deliberately deferred, not attempted this session** (see the
      new, narrower items just below): `float`/`clear` (a genuinely
      different, separate layout algorithm — text wrapping around a
      floated box — not just an extension of this positioning work);
      `position: sticky`; full CSS2.1 Appendix E stacking-context
      ordering (this session's `z-index` support is real but
      intentionally minimal — see its own item).

- [ ] `float`/`clear` are still entirely unparsed/unimplemented — a
      floated box needs to be taken out of normal flow *and* have
      surrounding inline content actually wrap around it (not just
      skip reserving space for it, which is all `position: absolute`
      needed): real extra complexity this session's positioning work
      doesn't cover at all. `clear` depends on knowing where any
      preceding float(s) in the same block formatting context actually
      ended up, so it can't be implemented independently of `float`
      itself.

- [ ] `position: sticky` isn't parsed — it falls through to `static`
      (same "reject a variant that needs fundamentally different
      machinery rather than approximate it" choice `box-shadow`'s
      `inset` rejection (v27) established — see `Position`'s own docs).
      Needs real scroll-position awareness (does this box's own
      would-be-static position fall outside the current scroll
      viewport in the "stuck" direction?) that re-evaluates every
      frame as `scroll_offset` changes — a materially different kind of
      input than anything `relative`/`absolute`/`fixed` need (all three
      resolve once, at layout time, and stay fixed until the next
      relayout). Scrolling in this engine is deliberately cheap
      precisely because it never touches layout at all (see NOTES.md's
      v4/v5 writeup) — making `sticky` work without reintroducing a
      per-scroll-tick relayout cost is a real design question of its
      own, not a drop-in extension of this session's work.

- [ ] This session's `z-index`/stacking-order support is real but
      narrower than the full CSS2.1 Appendix E model: every out-of-flow
      (`absolute`/`fixed`) box anchored to the same containing block
      paints in one ascending-`z-index` group, after that containing
      block's own normal content — correct for the common case (an
      overlay/dropdown/tooltip stacked above normal page content) but
      not real stacking-context semantics. Not modeled at all: negative
      `z-index` painting *below* its own containing block's background
      (every out-of-flow box here always paints on top of its own
      containing block, regardless of sign); a `position: relative`
      box (in normal flow, never taken out of it) establishing its own
      *separate* stacking context that would reorder its own in-flow
      descendants against unrelated content elsewhere on the page —
      `relative` here only ever gets *paint-position* treatment, never
      stacking-order treatment, since nothing yet makes two unrelated
      in-flow subtrees overlap in the first place; and `z-index` on
      anything other than a `position`-ed box (meaningless in real CSS
      too, so not a gap, just worth stating). Revisit once `float` (or
      anything else that can make ordinary in-flow content overlap)
      actually lands and this narrower model stops being sufficient.

- [ ] No flexbox (`display: flex`) or grid (`display: grid`) — `Display`
      only has Block/Inline/None/Table/TableRow/TableCell/TableGroup.
      `default.css` doesn't need either today, but most real-world pages
      do for their outer page chrome.

- [ ] Last member of what was once a cluster of CSS properties: `word-
      spacing` is still entirely unrecognized (dropped). Not just
      unimplemented but genuinely harder than `letter-spacing` was:
      cosmic-text 0.19's `Attrs` has no `word_spacing`/`word-spacing`
      API to hook into at all (confirmed by grepping its vendored
      source — `letter_spacing_opt` is the only tracking-style knob it
      exposes), so a correct implementation would mean hand-rolling
      word-boundary detection and extra spacing entirely outside
      cosmic-text's own shaping/wrapping — a worse-case version of the
      exact risk that already broke the `letter-spacing` attempt (the
      wrap width cosmic-text computes internally wouldn't know about
      space scratchy added after the fact). Nothing in `default.css`
      needs it. (`line-height` landed in v24, `visibility` in v25,
      `outline` in v26, `box-shadow` in v27, `border-radius` in v28,
      relative `font-size` keywords in v29, `border-style` in v30,
      `overflow` in v31, `cursor` in v32, `text-decoration-style`/
      `-color` in v33, `rem` in v34, `font-weight: bolder`/`lighter` in
      v35 — all previous cluster members, now resolved.)

- [ ] `text-decoration-style`/`-color` (PROMPTS.md v33) support
      `dashed`/`dotted` (hand-painted, since cosmic-text 0.19's own
      decoration renderer only knows a plain solid stroke) and an
      explicit color (native cosmic-text support, no hand-rolling
      needed) — plus `double`, which was already silently accepted
      before this but is now visually distinct (cosmic-text's own
      `UnderlineStyle::Double`, underline only). `wavy` has no custom
      painting path and falls back to `Solid` — an actual sine-wave
      stroke needs real curve rasterization this file doesn't have
      anywhere else. `double` only visibly differs for *underline* —
      cosmic-text 0.19 has no double variant for strikethrough/overline,
      so `text-decoration: line-through double` still paints one plain
      line, not two (undeclared in `default.css`, so not a regression
      for anything real). There's still no separate
      `text-decoration-style`/`-color` *longhand* support — only via the
      `text-decoration` shorthand, which is the only form `default.css`
      or any test page used.

- [ ] `cursor` (PROMPTS.md v32) only tracks `auto`/`pointer` — the one
      keyword `default.css` actually declares (`a { cursor: pointer }`).
      No `text`/`wait`/`crosshair`/`move`/`grab`/etc. (easy to add the
      same way if something needs one). **Not visually verified beyond
      headless tests + a crash/render smoke-test**: the OS cursor icon
      is rendered by the compositor, not scratchy's own pixel buffer,
      so `grim` screenshots can't show it, and this environment has no
      way to synthesize a real mouse-move event to drive it
      end-to-end. The hit-testing logic itself (glyph-precision —
      confirmed a link's own glyphs report `Pointer` while adjacent
      plain text reports `Auto`) and the `CursorStyle`→`CursorIcon`
      mapping are both verified directly; only the final
      `window.set_cursor` call and `WindowEvent::CursorMoved` wiring
      (thin, mechanical glue around already-tested logic) went
      untested live. Worth a real interactive check next time a human
      is at the keyboard.

- [ ] `overflow` (v31, extended to box decoration in v40) still only
      supports `visible`/`hidden` — no `scroll`/`auto` (no scrollbar UI,
      no interactive scroll region, just clipping).

- [ ] `border-style` (PROMPTS.md v30) only distinguishes `dashed`/
      `dotted`/`double`/`none`/`hidden` from a plain solid stroke —
      `groove`/`ridge`/`inset`/`outset` all fall back to rendering as
      `solid`, since a real bevel effect needs two-tone shading this
      file's flat-fill painting primitives don't have (`hr`'s
      `border-style: inset` in `default.css` already rendered solid
      before this property existed at all, so this is a no-op for it,
      not a regression). Revisit if a real page's bevel border looks
      visibly wrong as flat solid instead.

- [ ] `border-radius` (v38) combined with a non-`solid` `border-style`
      (`dashed`/`dotted`/`double`) falls back to the old square-corner
      rendering for both background and border — a rounded ring works
      for `solid` only (`fill_rounded_ring`). A correctly-rounded
      dashed/dotted ring needs the same curved-path tracing a solid
      ring does, just repeated per dash/dot/stripe along that curve
      instead of a straight edge — real extra work, not attempted here
      since nothing in `default.css` or a real test page needs it yet.

- [ ] **`opacity` was deliberately skipped, not attempted** — scoping
      it out surfaced a real design decision, not just an
      implementation task. Unlike every other paint-only property
      landed this session (`outline`/`box-shadow`/v12's
      `background-color`), `opacity` can't be resolved and applied
      purely within `resolve_style`/`paint`: real CSS opacity dims an
      element's *entire subtree* as one group (so a `<div
      style="opacity: 0.5">` with text inside dims the text too, not
      just the div's own background/border), which would mean
      threading a new accumulated-opacity parameter through all of
      `build_box_for_element`/`build_table_children`/
      `build_table_row_cells`/`build_children`/
      `build_children_with_prefix`/`collect_children` — a materially
      bigger, more invasive plumbing change than anything else done
      this run (every other ambient property so far only needed
      `collect_children` itself). Worse, a simplified "multiply each
      descendant's own alpha by an ambient accumulated opacity" isn't
      actually equivalent to real CSS opacity's group-compositing
      semantics — it'd visibly diverge for overlapping semi-transparent
      content (double-blending vs. single-group-composite), a
      correctness trade-off worth the user's input rather than a
      unilateral pick between that, a non-propagating
      own-element-only version (simpler but misleading — wouldn't dim
      a `<div opacity:0.5>`'s own text/children at all, surprising for
      the property's most common real use), or the invasive
      fully-correct plumbing.

- [ ] **`letter-spacing` was attempted and reverted (no commit) after
      finding what looks like a real cosmic-text 0.19.0 bug**, not a
      scratchy bug: `Attrs::letter_spacing()` is a real, documented
      API and wiring it in was mechanically straightforward (parsing,
      cascade, inheritance, `SpanStyle`/`shape_spans` threading — all
      implemented and headlessly verified correct in isolation, single
      span, no wrapping). The problem only showed up visually, on a
      real multi-word paragraph: cosmic-text's word-wrap line-breaking
      starts firing *far* too early once `letter-spacing` crosses a
      small threshold, shattering a paragraph that should easily fit
      on one line into one-word-per-line (worse: close to one-
      character-per-line at larger spacing values). Reproduced and
      measured in isolation (not an artifact of scratchy's own layout
      code): `"Wide letter spacing "` at 900px available width wraps
      to 1 line up to ~2px of spacing, 2 lines at 3-4px, 3 lines at
      5-7px, 4 lines at 8px — clearly the line-breaking pass is
      computing available width or word width wrong once
      `letter_spacing_opt` is set, even though the *final* rendered
      glyph x-advance (confirmed separately) correctly includes the
      spacing. This is squarely inside cosmic-text's shaping/layout
      internals (`src/shape.rs`/`src/layout.rs` in the vendored
      0.19.0 source), not something fixable from scratchy's call
      site. Needs either: confirming this against a newer cosmic-text
      release (not checked — no network access this session), finding
      an upstream issue/workaround, or accepting a documented
      limitation (e.g. only support small letter-spacing values, or
      disable wrapping whenever letter-spacing is set — both would be
      lossy enough to want explicit sign-off before shipping, which is
      why this was skipped rather than guessed at).

- [ ] `box-shadow` (PROMPTS.md v27) is deliberately narrower than the
      real property: no `inset` (rejected outright, not misrendered as
      an outer shadow), no blur (`blur-radius` is parsed so it doesn't
      drop the declaration, but discarded — every shadow is a
      hard-edged solid rect), no comma-separated multiple shadows
      (just the first/only one), and `color` is required (no
      `currentColor` fallback for an omitted color). Revisit if a real
      page's shadow looks visibly wrong without blur, or needs
      `currentColor`/multiple layered shadows.

- [ ] CSS custom properties (v45) only resolve `var()` against `:root`/
      `html`-scoped declarations — a flat, whole-document table, not
      real per-element cascade/inheritance. A `--name` declared on any
      other selector (scoping a variable to one subtree, e.g. `.dark-
      mode { --bg: ... }`) is invisible to `var()`. Doing this properly
      would mean threading a resolved-custom-props map through
      `resolve_style`'s per-element cascade plus a second, per-element
      substitution pass (an element's inherited custom props aren't
      known until its ancestors are resolved) — real, invasive plumbing
      on the order of the `opacity` item below, not attempted since
      nothing needs it yet. Also: one custom property's raw value is
      never itself substituted against another (`--b: var(--a)` inside
      a `:root` block won't resolve to `--a`'s value — only a `var()`
      *fallback* gets recursive substitution), and substitution is a
      text-level scan with no CSS string/comment awareness (`content:
      "var(--x)"` would still get substituted inside the quotes).

- [ ] No at-rules at all — `@media`, `@import`, `@font-face`,
      `@keyframes`, and transitions/animations are all skipped outright
      at the stylesheet-parsing stage (`TopLevelParser`'s `AtRule`
      parsing is a deliberate no-op). No responsive breakpoints, no
      animation of any kind.

- [ ] `OurSelectorImpl`'s `NonTSPseudoClass` (now `OurPseudoClass`,
      v37) still can't parse `:hover`/`:focus`/`:active` — unlike
      `:link`/`:visited`, those need real mouse-button/keyboard-focus
      state scratchy has no concept of tracking yet (only
      `WindowEvent::CursorMoved` position exists, and only for the
      `cursor` property, not selector re-matching/repaint-on-state-
      change).

- [ ] `<img>` (v46) only decodes a `data:` URI `src` (base64 form) —
      PNG/JPEG/GIF/WebP via the `image` crate. A local file path `src`
      is deliberately *not* read, even though nothing stops it
      technically the way real networking does — treated the same as
      the "no networking" stance until that's revisited, not a
      near-term gap. Sizing (intrinsic from the decoded image, CSS/HTML
      `width`/`height` overriding it, aspect-ratio-preserving when only
      one axis is set) and a missing/corrupt/unsupported `src` falling
      back to rendering `alt` text are both done. Two real simplifications
      left: no `object-fit`/`object-position` (an explicit `width` *and*
      `height` always stretches independently, real CSS's default
      `object-fit: fill` — nothing needs a different fit yet), and
      `blit_image` only nearest-neighbor scales (no bilinear/smoothing —
      a heavily downscaled photo will look aliased; revisit if a real
      page's scaled image looks visibly bad).

      **Not a bug — confirmed with the user:** an `<img>` with no
      sizing CSS and no `max-width` from the page's own stylesheet
      renders at full intrinsic size and can overflow the viewport
      (worse here than on a real browser since scratchy has no
      horizontal scrolling at all — the overflow is just clipped off-
      window with no way to reach it). This is genuinely spec-accurate:
      real browsers don't implicitly cap `<img>` width either — the
      "images never overflow" behavior people expect from the web
      almost always comes from a page's *own* author CSS (`img {
      max-width: 100% }`, often via a reset), not a UA default.
      `default.css` deliberately does *not* add that rule itself — the
      user was offered it as a pragmatic (non-spec) UA-level default
      and explicitly chose to keep matching real browser behavior
      instead. Don't "fix" the overflow by adding `img { max-width:
      100% }` to `default.css` without checking this decision still
      holds.

      **Real inline-level flow, resolved (v48):** a default-`display:
      inline` `<img>` now genuinely shares a line with surrounding text
      and wraps correctly — `collect_children` pushes it straight into
      the inline run as an `InlineItem::Image` instead of always
      flushing/breaking the line (an explicit `display: block`/`table`
      override still gets its own box, same as any other block
      element). Since cosmic-text's `Buffer` has no concept of an
      embedded non-text box mid-paragraph, `measure_mixed_inline` hand-
      rolls its own greedy line-breaker whenever a run contains an
      image: splits text into words, shapes each word as its own tiny
      one-span paragraph via the existing `shape_spans`/`ShapeCache`
      machinery (full per-word fidelity — color/background/decoration/
      cursor all still work, participates in the same incremental
      shaping budget as a whole paragraph would), and positions words +
      image(s) left-to-right with wrapping. A plain-text-only run is
      entirely unaffected — same single-`Buffer`-per-paragraph fast path
      as before, only a run that actually contains an image takes this
      new, more expensive route.

      Known simplifications in `measure_mixed_inline` specifically (see
      its own doc comment for the full list): no cross-word kerning/
      ligatures (each word shaped independently); no real bidi
      reordering across words in a mixed run (cosmic-text's own bidi
      only operates within one `Buffer`, and this shapes one per word —
      RTL text spanning multiple words next to an image would appear in
      the wrong visual order); `white-space: pre` isn't honored in a
      mixed run (words always split on plain spaces, no embedded-`\n`
      awareness); an inline `<img>`'s vertical margin is ignored
      (horizontal margin correctly reserves line space); an image is
      bottom-aligned within its line as an approximation of real CSS
      baseline alignment (the actual font-metrics baseline offset isn't
      threaded out of cosmic-text here); only `text-align: left/right/
      center` apply to a mixed line (`justify` falls back to `left` —
      no inter-word space stretching); a line's trailing space counts
      toward its width for alignment purposes, unlike a real UA which
      hangs trailing whitespace past the edge.

- [ ] `background-image` (v47) only decodes a `data:` URI `url(...)` —
      same policy as `<img src>` (see `decode_data_uri`'s own docs and
      the `<img>` item above) — and only the unqualified default
      rendering: tiled at the image's own intrinsic size
      (`background-repeat: repeat`, `background-position: 0 0`). No
      `background-size`/`background-position`/`background-repeat`
      longhand control at all (so no `cover`/`contain`/`no-repeat`/
      centering/offset positioning), no comma-separated multiple
      background-images, and `background-image: none` isn't recognized
      as its own value (parsing it just fails, which happens to leave
      the property unset — the right end state today, but would be
      wrong if a lower-specificity rule *also* declared an image, since
      cascading wouldn't see `none` as a real override). The tiled image
      also isn't clipped to `border-radius`'s rounded corners — square
      tile edges regardless. Revisit any of this once a real page's
      background-image needs `cover`/`no-repeat`/positioning to look
      right, rather than guessing at scope now.

- [ ] No forms/interactive widgets (`input`/`button`/`select`/
      `textarea` render as plain unstyled DOM nodes, not widgets), no
      replaced/embedded elements (`img`/`svg`/`canvas`/`video`/`audio`/
      `iframe`/`object`/`embed` have no special handling or box model —
      nothing to draw anyway with no networking), and no JavaScript
      (html5ever only parses the DOM; `<script>` contents are read and
      discarded, never executed). The only interactivity scratchy has
      at all is mouse-wheel scroll and window resize — no link
      navigation, no keyboard input, no text selection. Networking
      itself (fetching the page, images, fonts, external stylesheets)
      remains a deliberately separate, not-yet-started concern from
      rendering — see NOTES.md.
