scratchy — known gaps / deferred work

Plain checklist of things found-and-deliberately-deferred during work on
this project, so they don't get forgotten between sessions. Not a
feature backlog of things nobody asked for — only things we actually
hit and chose not to fix immediately. See NOTES.md for the fuller story
behind any item; a commit hash in parens points at the commit it came
up during (`git show <hash>`) — more precise than a PROMPTS.md version
number, since several versions can share one commit and a hash is
directly actionable. PROMPTS.md is append-only and never edited for
these.

- [x] `%` lengths (v49): `width`/`height` and their `min-`/`max-` forms,
      `margin`/`padding` (all four sides, including top/bottom — real
      CSS resolves a margin/padding `%` against the containing block's
      *width* on every side), `border-radius` (against this box's own
      border-box width), `font-size` (against the parent's font-size,
      same timing as `em`), and `line-height` (against the declaring
      element's own font-size) all now accept `%`. `width`/margin/
      padding/`border-radius` resolve against a containing-block
      dimension that isn't known until layout (`measure`, not
      `resolve_style`) — see `BoxLength`'s own docs for the deferred-
      resolution mechanism this needed. `height`/`min-height`/
      `max-height` follow the real spec rule for an indefinite
      containing block height (an ordinary `height: auto` ancestor):
      the percentage computes to `auto`, i.e. has no effect at all,
      exactly as if it weren't declared — not resolved against some
      made-up basis. `border-width`/`outline-width`/`box-shadow`'s
      offsets/blur/spread deliberately still reject `%` — the real CSS
      grammar for all of them is `<length>`, not `<length-percentage>`,
      so accepting a percentage there would be adding something the
      spec itself doesn't allow, not closing a gap.

      Unitless numbers (besides literal `0`) were also checked per this
      item's original wording: still correctly rejected everywhere
      except `line-height` (already valid pre-v49 — a bare `<number>`
      is that property's own real grammar, the single most common
      real-world form) — confirmed by grep and a permanent test, not
      changed, since real CSS doesn't allow a unitless non-zero number
      for any other property scratchy supports (`z-index`/`flex`/etc.,
      where it would be valid, aren't implemented at all).

      - [ ] No viewport/initial-containing-block height concept exists
            (v49) — unlike a real UA, whose initial containing block
            always has the window's own definite height, this engine's
            document-root box (a synthetic wrapper `<html>` is laid out
            *inside*, not literally the tree's root) has no height of
            its own, so the classic `html, body { height: 100% }`
            full-height pattern doesn't resolve to anything (same as
            not declaring it) — only an ordinary nested `%` height
            against an *explicit* ancestor height works. Tried wiring
            the window's own inner height through as the top-level
            `measure` call's `containing_height`, and reverted it: that
            value is also reused as the "total scrollable content
            height" `redraw`'s own scroll-clamping reads directly off
            the root `Laid`'s `h` — pinning it to the window's height
            would silently cap every page at exactly one viewport's
            worth of scrollable content, a real regression to actual
            scrolling, not a hypothetical one. Needs the root box's
            "containing-block-height" role and its "total content
            height for scrolling" role separated before this can be
            revisited, not a one-line fix.

- [x] Table layout (53bab7a) now does real CSS2.1 §17.5.2.2
      automatic table layout: each column's width is sized from the
      min/max content width of its own cells (`cell_natural_width`,
      distributed across the table's own content width by the real
      spec three-case rule — grow to fill if every column's max-content
      width fits, shrink proportionally if even every column's
      min-content width doesn't, interpolate between min and max
      otherwise), not the old equal-width-column split. One deliberate
      divergence from the literal spec, kept from before this item
      landed: a real auto-width table shrink-wraps to its own content;
      this one still stretches to fill its container (an auto `Blocks`
      box's existing behavior) — changing that is a separate, bigger
      scope than "size the columns from their content."

      Still out of scope, unchanged from before this item: no
      colspan/rowspan (default.css/real-world markup don't need them
      for anything scratchy renders yet), no border-collapse/borders-
      between-cells (default.css doesn't declare any table/cell
      borders), no `caption-side` placement (caption always renders in
      source position, which is first — same as the default anyway).
      One narrower gap newly surfaced by real column sizing: an
      explicit `width`/`min-width`/`max-width` set directly on a
      `<td>`/`<th>`, or a `<col width>`/CSS `width` on a `col`/
      `colgroup`, isn't honored as a column-sizing hint — only a cell's
      own *content* drives its column's width.

- [x] `font-family` (PROMPTS.md v16, named families/fallback lists:
      v51) now parses a real comma-separated fallback list — a quoted
      string (`"Georgia"`), an unquoted multi-word name joined with
      spaces (`Helvetica Neue`), and any of the 5 bare generic keywords,
      in any mix and order. Resolution against the real font system
      (not just the cascade) tries each named family in order and falls
      back to the next — or the trailing generic — exactly the way real
      CSS `font-family` fallback works: `fontdb::Database::query`
      already implements this in-order "first family with any installed
      face wins" search internally (confirmed by reading its vendored
      source, not assumed), queried one candidate at a time since
      `cosmic_text::Attrs::family` itself can only ever hold one
      resolved `Family`, not a list. Verified past the cascade: a
      permanent test shapes a list naming an impossible family before a
      real `monospace` keyword and confirms the shaped `cosmic_text::
      Buffer` actually lands on monospace's own `fontdb::ID`, not
      cosmic-text's default sans-serif. Also visually confirmed with a
      real `grim` screenshot against an installed named family
      (`Liberation Serif`) and both fallback cases.

      One architectural note worth flagging for a similar future
      property: `FontFamily` had to become a leaked `&'static` slice
      (`Box::leak`, once per distinct parsed declaration) rather than an
      owned `Vec`, specifically so `ComputedStyle`/`InheritedStyle`/
      `SpanStyle` could keep their existing `#[derive(Clone, Copy)]` —
      see PROMPTS.md v51 and NOTES.md v34's own note on this exact
      tradeoff for the full reasoning. Not a correctness gap, just a
      memory-reclamation one: a distinct `font-family` declaration's
      parsed list is never freed for the life of the process (bounded by
      how many distinct declarations a document's CSS has, not by
      element/redraw count — see PROMPTS.md v51 for why this was judged
      an acceptable, not a new-category, cost).

- [x] `text-decoration` (PROMPTS.md v17) originally only tracked the line
      keywords (underline/line-through/overline/none) — `dashed`/`dotted`/
      `double`/`color` now paint correctly too (PROMPTS.md v33, confirmed
      still true by grepping `parse_text_decoration`/`DecorationStyle` in
      `src/lib.rs` during the 2026-10-29 autonomous TODO.txt pass — this
      item was already fully resolved, just never checked off). See the
      `text-decoration-style`/`-color` item below for what's still open
      (that's a narrower, separate gap, not this one).
      `abbr[title] { text-decoration: dotted underline }` in default.css
      now actually renders dotted, not a plain solid underline.

- [x] `<title>`/`<head>` now hidden (PROMPTS.md v53): `head, title, meta,
      link, base, noscript { display: none; }` added to `default.css`,
      narrowed from the WHATWG spec's full hidden-elements list to the
      tags scratchy actually parses. `head` resolving to `display: none`
      alone is enough for its children too (`collect_children` never
      recurses into a `Display::None` element), but the other tags are
      listed explicitly to match the real spec and stay correct even if
      one ends up outside `<head>` in a given document.

The rest of this file is a full html-rendering feature-gap survey done
after v20 (commit 7950fc2), not individual things hit mid-feature like
the items above — see the conversation that asked "what features are
missing in regards to rendering html?" Grouped by area so a future
session can pick a coherent slice rather than one property at a time.

- [x] `position: relative`/`absolute`/`fixed` (bb97e60) now
      work: `relative` offsets a box's painted position (`top`/`right`/
      `bottom`/`left`, px/`%`/`em`/`rem`) without affecting normal flow
      at all (siblings land exactly where they would if it had no
      offset); `absolute`/`fixed` are genuinely taken out of flow (no
      space reserved for them by their own parent) and positioned
      against the padding box of the nearest ancestor whose own
      `position` isn't `static` (`absolute`) or the viewport
      (`fixed`, immune to scroll — an orphaned `absolute` with no
      positioned ancestor anywhere above it uses the same viewport-
      sized rect, approximating the real CSS initial containing block).
      `z-index` (plain integer, `auto`/unset treated as `0`) controls
      paint/hit-test order *among boxes that share the same containing
      block* — out-of-flow descendants always paint after their
      containing block's own normal content, ascending by `z-index`,
      ties in document order. Real CSS §9.7's "computed `display`"
      rule is applied too: an `absolute`/`fixed` element's `display`
      always computes to `block` (unless it's `none`), so e.g. a
      `<span style="position: absolute">` gets its own box instead of
      being flattened into the surrounding inline run. 7 new permanent
      tests cover: relative offset leaving sibling flow untouched;
      relative `%` offset resolving against the containing block;
      absolute removed from flow + anchored to a positioned ancestor's
      padding box; absolute solving `right`/`bottom` from its own
      measured size; an orphaned absolute and a `fixed` box both
      bubbling to the document root (same containing-block rect,
      different scroll behavior); fixed staying anchored to the
      viewport regardless of a 3000px-tall preceding sibling; and a
      real painted-pixel check that a higher-`z-index` box wins an
      overlap despite appearing earlier in document order.

      **Deliberately deferred, not attempted this session** (see the
      new, narrower items just below): `float`/`clear` (a genuinely
      different, separate layout algorithm — text wrapping around a
      floated box — not just an extension of this positioning work);
      `position: sticky`; full CSS2.1 Appendix E stacking-context
      ordering (this session's `z-index` support is real but
      intentionally minimal — see its own item).

- [x] `float: left`/`right` (5fc83ce) now takes a box out
      of normal block-level flow (no vertical space reserved for it by
      its own parent, same as `position: absolute`) but, unlike
      `absolute`, still participates in the surrounding *inline*
      formatting context: a later sibling's own text genuinely wraps
      around it — narrower lines while they overlap its vertical range,
      full width again once past it — not just a block-level
      skip-reserving-space approximation. `clear: left`/`right`/`both`
      moves a box down past the bottom of any earlier same-BFC float on
      the named side(s) (CSS2.1 §9.5.2). A `width: auto` float uses real
      shrink-to-fit sizing (§10.3.5), not "fill the container" the way
      an ordinary auto-width block does. Real CSS's own "computed
      `display`" rule (§9.7) applies to `float` too, same as `position`
      already got in v52. A float now also paints *above* a later,
      non-cleared, full-width sibling's own background where they
      legitimately overlap (real CSS2.1 Appendix E stacking order for
      floats vs. ordinary in-flow block boxes) — found as a real,
      visible bug via a screenshot mid-session, not a hypothetical edge
      case.

      A few narrower things deliberately not attempted, scoped out
      rather than silently folded into "done":

      - [ ] Multiple floats competing for the same side at the same
            flow position don't get CSS2.1 §9.5.1's full placement
            algorithm — a float whose own (shrink-to-fit or explicit)
            width doesn't actually fit in the corridor earlier same-side
            floats leave at that exact `y` is placed there anyway rather
            than retried further down, and may visually overlap a
            competing float. Also in this same narrower bucket: once
            *any* float exists anywhere earlier in a block formatting
            context, every paragraph that starts before the *lowest*
            float's own bottom edge takes the slower per-word line-
            breaking path (`measure_mixed_inline`, reused from v48's
            inline-image flow) rather than cosmic-text's fast whole-
            buffer shape — including a paragraph that turns out not to
            overlap any specific float once its own lines are actually
            positioned. And a float's own cursor-hit-test priority still
            follows plain document order (first match wins, like any
            other `Blocks` sibling) rather than the paint order fixed
            above, so a click in a float/later-sibling overlap region
            may resolve against whichever one happens to come first in
            the markup, not whichever one is actually on top. None of
            these affect the common single-float case this item's own
            tests/screenshots cover.

- [x] `position: sticky` (636f369) now parses and works —
      per the user's own explicit design decision (asked via
      `AskUserQuestion`, see PROMPTS.md's v55 entry), resolved with
      *no* relayout cost from scrolling: a sticky box's own would-be-
      static position and its real (parent/content-box) containing
      block's vertical extent are resolved once, at layout time,
      exactly the same way `relative`'s own offset basis already is
      (`capture_sticky_info`/`patch_sticky_containing_block`, stored in
      a new `Laid::sticky: Option<StickyInfo>` field) — the box stays
      in normal flow throughout, contributing to its container's size
      and never disturbing sibling positions, same as `relative`. The
      actual *painted* position is computed fresh every frame from the
      live `scroll_offset`, entirely in `paint`/`hit_test_cursor`
      (`sticky_shift`), by folding the computed shift into the
      *ambient* scroll offset passed down into that one child's
      recursive call — the exact same trick `position: fixed` (v52)
      already uses to make its own subtree scroll-independent, reused
      here instead of invented fresh. `measure`/`Laid` never read
      `scroll_offset` at all, so a scroll-offset change genuinely can't
      trigger a relayout — `paint` takes `&Laid`, not `&mut Laid`, a
      compile-time guarantee, not just a runtime one (pinned by a
      permanent test).

      Only `top`/`bottom` are resolved — scratchy has no horizontal
      scrolling at all, so a `left`/`right` sticky offset would have no
      live horizontal scroll position to clamp against; deliberately
      not attempted (`top` wins over `bottom` when both are set, same
      precedence `resolve_positioned` already gives `left`/`top` over
      `right`/`bottom`). Doesn't force computed `display: block` the
      way `absolute`/`fixed` do (real CSS §9.7 only names those two) —
      an inline `position: sticky` element stays flattened into its
      surrounding run with no box of its own to stick, the same
      pre-existing gap `relative` already has on inline content, not
      newly introduced here. A `<tr>`/`<td>` itself declaring `position:
      sticky` (the classic "sticky table header row" case) isn't
      supported either — same pre-existing scope cut `position:
      absolute`/`fixed` already have for table rows/cells (see v52).
      Only one scrolling container exists in this engine at all (the
      whole document/viewport — no nested `overflow: scroll`/`auto`
      region exists to need its own sticky-clamping logic), so "nearest
      scrolling ancestor" was simplified to exactly that, per the
      user's own explicit sign-off.

      5 new permanent tests. **Not live-verified interactively, flagged
      rather than glossed over, same category v32's `cursor` and v52's
      `fixed`-while-scrolling gaps already established**: this sandbox
      has no tool to synthesize a real mouse-wheel/scroll event (no
      `wtype`/`ydotool`/`wlrctl`, confirmed by checking), so the actual
      live "does it visually stick, then release, while scrolling with
      a real mouse" behavior couldn't be driven end-to-end — only
      confirmed via `grim` that a sticky box renders correctly at its
      *static* (pre-scroll) position on first paint. The underlying
      mechanism is directly exercised by permanent headless tests
      (`sticky_box_paints_at_its_static_position_before_scroll_reaches_
      the_threshold`, `sticky_box_clamps_to_its_top_offset_once_scroll_
      passes_the_threshold`, `sticky_box_stops_sticking_once_its_
      containing_blocks_far_edge_would_scroll_past`, each calling the
      real `paint`/`sticky_shift` code path with a real measured
      `Laid` tree, not just asserting the math in isolation). Worth a
      real interactive check next time a human's at the keyboard.

- [x] Real CSS2.1 Appendix E stacking-context semantics (v56, bc3b696): the
      seven-layer bottom-to-top paint order
      (https://www.w3.org/TR/CSS21/zindex.html) is now genuinely modeled
      per stacking context — (1) this box's own background/border, (2)
      negative-`z-index` descendant stacking contexts, (3) in-flow
      non-positioned non-floated block descendants, (4) floats, (5)
      in-flow inline descendants, (6) `z-index: 0`/`auto` positioned
      descendants, (7) positive-`z-index` descendant stacking contexts —
      verified layer-by-layer with a permanent pixel test, not assumed.
      Two concrete fixes over the old, narrower model (every out-of-flow
      box used to paint in one flat ascending-`z-index` group, always
      *after* its containing block's own content, regardless of sign):

      Negative `z-index` now paints *above* its own containing/stacking-
      context box's own background/border but *below* that box's normal
      content (layer 2 sits between layers 1 and 3). Checked directly
      against the spec rather than assumed: the intuitive "negative
      z-index hides behind its own box's background" is a common but
      *inaccurate* paraphrase of the real rule — Appendix E lists
      background (layer 1) *before* negative stacking contexts (layer 2)
      in its bottommost-first order, meaning negative paints on top of
      it; it only looks "hidden behind everything" when the relevant box
      happens to have no background of its own, leaving nothing else for
      it to appear in front of.

      `position: relative`/`sticky` with an *explicit* `z-index` now
      establishes its own descendant stacking context (real CSS2
      §9.9.1) — pulled out of plain document-order painting to compete
      by `z-index` with its containing block's other out-of-flow
      descendants instead, the same way `absolute`/`fixed` already did.
      `z-index: auto` on `relative`/`sticky` is unaffected (still
      today's plain paint-position-only treatment — real CSS: `auto`
      does not establish a stacking context).

      The "two unrelated in-flow subtrees overlapping" generality the
      original item worried about turned out to be reachable, just not
      in the unbounded way the old wording implied: a `position:
      relative` box's own offset can already overlap a *sibling* in the
      same parent's `Blocks` list (float/clear, v54, only narrows
      content *around* a float — it doesn't let two unrelated block
      subtrees overlap arbitrarily anywhere on the page). Scoped to
      exactly that reachable case — sibling-level, same immediate parent
      — rather than building a fully general cross-subtree stacking
      search for a case that doesn't occur in this layout model.

      Deliberately scoped out, each documented precisely rather than
      silently dropped:
      - [ ] A `relative`/`sticky` box's own explicit-`z-index` stacking
            context is always anchored at its *immediate* containing
            block (the same box that already catches its own
            `absolute`/`fixed` descendants), never bubbled past an
            intervening ancestor that is itself positioned but has
            `z-index: auto` — real CSS would let such an ancestor's own
            descendants' `z-index` comparisons bubble further up past it
            (an auto-`z-index` positioned box doesn't establish its own
            context), which this doesn't model. Not reachable by
            anything `default.css` or a real test page needs yet (deep
            nested positioned-with-auto-`z-index` ancestors containing
            an explicitly-`z-index`ed descendant are uncommon), but a
            real, narrower gap than the general case this item used to
            describe.
      - [ ] `hit_test_cursor`'s negative-`z-index` priority doesn't fully
            mirror `paint`'s now-corrected order: a negative stacking
            entry (an out-of-flow box or an explicit-`z-index`
            `relative`/`sticky` child) is still checked at the same
            (highest) hit-test priority as a non-negative one, rather
            than only after normal content the way it now actually
            paints — same category of approximation `float`'s own
            cursor-hit-test priority already has (v54): correct for the
            common case (nothing else covers the same pixel), wrong only
            when a negative stacking entry and normal content genuinely
            overlap at the exact same screen pixel.

- [x] `display: flex` (440e03b) now does real CSS Flexible Box
      Layout (https://www.w3.org/TR/css-flexbox-1/), scoped to the common
      "flex row/column of items, growing/shrinking/justified/aligned"
      case — grid explicitly deferred, see its own item just below (same
      "bundling both would risk landing neither well" latitude the
      `position`/`float` items already used). Landed: `flex-direction`
      (`row`/`row-reverse`/`column`/`column-reverse`), `flex-wrap`
      (`nowrap`/`wrap`/`wrap-reverse` — real for `row`/`row-reverse`
      only, see its own item below), `flex-flow` shorthand,
      `justify-content` (all 6 keywords, including `space-evenly`, which
      the original task wording treated as optional — it fell out of the
      same arithmetic as `space-between`/`space-around` for free),
      `align-items`/`align-self` (`flex-start`/`flex-end`/`center`/
      `stretch`/`baseline` — `baseline` approximates to `flex-start`, see
      its own item below), `flex-grow`/`flex-shrink`/`flex-basis` and the
      `flex` shorthand (real proportional space distribution — verified
      with permanent tests that growth/shrink is genuinely proportional
      to the declared factors, not just "fits content"), and
      `gap`/`row-gap`/`column-gap` (new — nothing in this codebase had
      `gap` before). `order` was deliberately not attempted (see its own
      item below). `inline-flex` was not attempted either — a flex
      container is always block-level in the outer flow here (same as
      `display: table`); real `inline-flex` would need the same hand-
      rolled inline-level embedding `measure_mixed_inline` (v48) built
      for `<img>`, not attempted for this item.

      Architecturally: a new `BoxContent::Blocks`-shaped build path
      (`build_flex_children`, parallel to `build_table_children`) plus
      `measure_flex`/`measure_flex_row`/`measure_flex_column` (parallel
      to `measure_table`/`measure_row_with_widths`), reusing `box_model_
      entry` for the container's own box model and `cell_natural_width`
      (v50's min/max-content measurement, originally built for table
      columns, already reused once for `float`'s shrink-to-fit sizing —
      now a third use) for a `width`-axis item's content-based basis. See
      NOTES.md for the full architecture writeup, including the one
      real insight that made cross-axis stretch/grow/shrink cheap: this
      engine's own `height` property already doesn't affect how a box's
      children are laid out (v42), so a flexed/stretched final size on
      whichever axis is *height* is a pure post-hoc `Laid::h` overwrite,
      never a second `measure()` call.

      **Deliberately cut within flexbox itself, each precise and
      documented, not silently dropped:**

      - [ ] `order` is not implemented — every flex item lays out (and
            paints/hit-tests) in plain document order, `row-reverse`/
            `column-reverse` only mirror *position* along the main axis,
            not reordering anything. Nothing in `default.css` or a real
            test page needs it yet; same shape of cut `z-index`'s own
            stacking-context work (v56) left for an analogous "not
            reachable by anything real yet" reason.
      - [ ] `align-content` (multi-line cross-axis distribution — e.g.
            spreading several wrapped lines apart when a `flex-wrap`
            container's own cross size is larger than its lines' summed
            cross size) isn't implemented — lines always stack with no
            extra distribution (`align-content: flex-start`'s behavior
            unconditionally). Not in this item's own requirements list;
            flagged here for completeness since `flex-wrap` is real.
      - [ ] `flex-wrap` is only genuinely real for `flex-direction: row`/
            `row-reverse` — a `column`/`column-reverse` flex container
            always lays its items out as a single column regardless of
            the declared `flex-wrap` value. Wrapping a *column* means
            wrapping across the *width* into multiple side-by-side
            columns, a materially different (and much rarer in real page
            chrome) shape than the classic wrapped-multi-line-row case
            this item prioritized — see `measure_flex_column`'s own docs.
      - [ ] `align-items`/`align-self: baseline` resolves identically to
            `flex-start` — real baseline alignment needs each item's own
            font ascent threaded out of `measure`'s box-model math (no
            box here tracks its own baseline today, only cosmic-text's
            per-glyph shaping does, several layers below `measure`) — a
            disproportionate amount of new plumbing for a value most
            real "flex row of items" pages don't rely on. Explicitly
            permitted as an approximation by this item's own task
            wording, not silently dropped.
      - [ ] No CSS Flexbox §9.7 iterative constraint resolution — `flex-
            grow`/`flex-shrink` distribution (`resolve_flex_main_sizes`)
            is a single pass: an item whose flexed size gets clamped by
            its own `min-width`/`max-width`/`min-height`/`max-height`
            doesn't have its own under/overshoot redistributed a second
            time among its unclamped siblings, the way the real spec's
            freeze-and-retry algorithm would. Fine for the common case
            (no unusually tight min/max relative to an item's own
            basis); a real divergence only once several siblings'
            constraints interact non-trivially.
      - [ ] No CSS Flexbox "automatic minimum size" — an item's own
            `min-width`/`min-height` only clamps if explicitly declared;
            there's no implicit min-content floor preventing `flex-
            shrink` from shrinking an item's content below its own
            natural min-content width/height the way real Flexbox does
            by default (`overflow: visible`'s own automatic-minimum-size
            rule, CSS Flexbox §4.5) — an item can shrink to (or past)
            zero, clipping/overflowing its own content, if nothing else
            stops it.
      - [ ] On a `flex-direction: row`/`row-reverse` container, an
            item's own explicit, conflicting CSS `width` wins over a
            flex-grown/shrunk main size (the distributed size is still
            passed as `measure`'s ordinary `width` parameter — correct
            whenever the item's own CSS `width` is `auto`, the common
            case — but `clamp_box_dim` uses an explicit `width` instead
            whenever one's declared, ignoring what's passed in). Same
            accepted simplification `measure_table`'s own per-cell
            `width`-vs-column-width gap already has (see its own
            `TODO.txt` item) — not reachable this way on a `column`
            container, where the equivalent override is a pure post-hoc
            `Laid::h` write that always applies regardless (see
            `measure_flex_column`'s own docs for exactly why the two
            axes differ here).
      - [ ] A bare, non-whitespace text node placed directly inside a
            flex container (no wrapping element) doesn't become its own

      inline` `<img>` now genuinely shares a line with surrounding text

      new, more expensive route.

      its own doc comment for the full list): no cross-word kerning/
      ligatures (each word shaped independently); no real bidi
      reordering across words in a mixed run (cosmic-text's own bidi
      only operates within one `Buffer`, and this shapes one per word —

      the wrong visual order); `white-space: pre` isn't honored in a

      baseline alignment (the actual font-metrics baseline offset isn't
      threaded out of cosmic-text here); only `text-align: left/right/
      center` apply to a mixed line (`justify` falls back to `left` —
      no inter-word space stretching); a line's trailing space counts
      toward its width for alignment purposes, unlike a real UA which
      hangs trailing whitespace past the edge.

- [ ] `background-image` (v47) only decodes a `data:` URI `url(...)` —
      same policy as `<img src>` (see `decode_data_uri`'s own docs and
      the `<img>` item above) — and only the unqualified default
      rendering: tiled at the image's own intrinsic size
      (`background-repeat: repeat`, `background-position: 0 0`). No
      `background-size`/`background-position`/`background-repeat`
      longhand control at all (so no `cover`/`contain`/`no-repeat`/
      centering/offset positioning), no comma-separated multiple
      background-images, and `background-image: none` isn't recognized
      as its own value (parsing it just fails, which happens to leave
      the property unset — the right end state today, but would be
      wrong if a lower-specificity rule *also* declared an image, since
      cascading wouldn't see `none` as a real override). The tiled image
      also isn't clipped to `border-radius`'s rounded corners — square
      tile edges regardless. Revisit any of this once a real page's
      background-image needs `cover`/`no-repeat`/positioning to look
      right, rather than guessing at scope now.

- [ ] No forms/interactive widgets (`input`/`button`/`select`/
      `textarea` render as plain unstyled DOM nodes, not widgets), no
      replaced/embedded elements (`img`/`svg`/`canvas`/`video`/`audio`/
      `iframe`/`object`/`embed` have no special handling or box model —
      nothing to draw anyway with no networking), and no JavaScript
      (html5ever only parses the DOM; `<script>` contents are read and
      discarded, never executed). The only interactivity scratchy has
      at all is mouse-wheel scroll and window resize — no link
      navigation, no keyboard input, no text selection. Networking
      itself (fetching the page, images, fonts, external stylesheets)
      remains a deliberately separate, not-yet-started concern from
      rendering — see NOTES.md.
