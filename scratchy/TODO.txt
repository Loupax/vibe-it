QSTASH — persistent web storage (user design session 2026-11-19; full design in STASH.md)
========================================================================

- QSTASH-D DESIGN (user, 2026-11-19; PROPOSED, DECIDED when the PR adding STASH.md
  merges; the items below follow STASH.md, not this summary): NO stash daemon. The
  filesystem is the backend interface: `--state-dir DIR` (default
  $XDG_STATE_HOME/scratchy, mode 0700; tmpfs = in-memory across scratchy restarts).
  localStorage = one FILE PER KEY under storage/<site>/<origin>/ (site schemeful as
  net_policy::site_of, `://` -> `!`; origin `scheme!host!port`); value = WTF-8 + one
  `\n`, reading strips one trailing `\n`; dotfiles and `*~` ignored; hand edits
  supported. Load once before the first script, no IO while JS runs, ops batched per
  task to a writer thread (temp file + fsync + rename / unlink). flock per site on
  storage/.locks/<site> (outside the data, never deleted; holds a generation number
  bumped by forget-site). No storage mutex, no cross-window storage events (same as
  browsers). sessionStorage never on disk. wire keeps the jar, gains --cookie-file.
  History: not now (waits for a reader). Supersedes QF-D7 for these stores.

QKEYS — input mode / normal mode, Esc Esc, `i`, status bar (user design session 2026-11-20)
========================================================================

- QKEYS-D DESIGN (user, 2026-11-20). THE STATE MACHINE IS IN KEYS.md (modes, diagram,
  transition table T1-T34): items follow KEYS.md; on any conflict with this text KEYS.md
  wins. This text is the decision history. Replaces the bare-key vim bindings that are always on
  ([archived: TODO-DONE.txt] "Vim-inspired keybindings + a `:` command bar") as the way keys
  are shared between the page and scratchy.
  PROBLEM: today every key goes to the page's keydown handlers first, and any key the page
  does not cancel falls through to scratchy's bare `j k h l g G :`. That breaks both ways:
  (1) scratchy steals keys pages use without preventDefault (YouTube `l` seeks AND goes
  history-forward, `k` pauses AND scrolls; GitHub/Gmail/Reddit `j/k`, `g` prefixes);
  (2) pages steal scratchy's keys (QJ11: vim.js on social.loupax.com cancels `:`, so the
  command line can't be reached; only SIGUSR1 gets you out). Per-key fixes can't solve it:
  the two sides fight over the same bare keys.
  Rejected triggers: holding Ctrl (Ctrl chords are what pages and text fields use: Ctrl-K
  palettes, Ctrl-Enter, Ctrl-A/C/V/W/H in inputs; would break copy/paste in fields);
  double-tapping a lone Ctrl or any other lone modifier (impossible with home-row mods,
  e.g. the user's Corne where Ctrl is a held `a`; same for a tap-hold Caps Lock).
  DECIDED (user 2026-11-20):
  D1 Two modes. INPUT MODE: scratchy claims no key except the Esc Esc trigger, and every
     key goes to the page and to the UA defaults (text controls, selects, Tab focus, media
     keys, as today). NORMAL MODE: scratchy's bindings (today's `resolve_binding` set:
     j k h l gg G Ctrl-d Ctrl-u Home End :) own every key.
  D2 Trigger: Esc pressed twice (two non-repeat presses, no other key between, within
     `ESC_ESC_MS` = 300, a const next to `resolve_binding`, dwm config.h style, so a QMK
     user can swap in F13 etc. in one line) enters normal mode from input mode. The first
     Esc still goes to the page as usual (closes its modal, blurs a focused text control as
     today); the second Esc is not delivered to the page.
  D3 An always-visible STATUS BAR at the bottom of the window shows the current mode
     (INPUT / NORMAL; the `:` command line takes the same strip while in command mode).
     Unlike today's `:` bar (painted OVER the page, paint_command_bar), it RESERVES its
     height: the page viewport (layout height, `innerHeight`, scroll max, hit-testing,
     the JS thread's GeomCache viewport) is the window minus the bar.
  D4 scratchy STARTS IN INPUT MODE (for now), at process start. A navigation does NOT
     reset the mode (D5: sticky), so `h h h` in normal mode walks back through history.
  D5 (user 2026-11-20) The mode that isn't INPUT is called NORMAL (vim's name), in the
     status bar and in code/docs ("normal mode"). Modes are STICKY unless a rule here says
     otherwise: normal mode stays on until left, so `jjjj` works (not one-shot like a tmux
     prefix). A single Esc leaves it (back to input mode). Esc in the `:` command line goes
     back to normal mode, as it goes back to Normal today.
     [SUPERSEDED by D6 the same day: Esc no longer leaves normal mode, `i` does.]
  D6 (user 2026-11-20, with /search in mind) `i` leaves normal mode for input mode (like vim's
     insert: "hand the keyboard to the page"). Esc in normal mode NEVER changes the mode; it
     only cancels (clears search highlights, a pending `g`). So: Esc Esc = keyboard to
     scratchy, `i` = keyboard to the page. You leave normal mode only on purpose, when a page
     needs its own keys; that is also why modes stay sticky across navigations (D4).
  D7 (user 2026-11-20) The modes and their kind:
       INPUT    sticky    -> NORMAL by Esc Esc
       NORMAL   sticky    -> INPUT by `i` (or P4's click into a text control/select)
       COMMAND  one line  `:` from NORMAL; Enter runs, Esc cancels; both back to NORMAL
       SEARCH   one line  `/` from NORMAL; Enter commits, Esc cancels; both back to NORMAL
     COMMAND and SEARCH are the stated exceptions to D5's stickiness.
  D9 (user 2026-11-20) "page mode" is renamed INPUT MODE ("input passthrough"), status bar
     `INPUT`; the text in this block was renamed to match. The design is written as a
     state machine in KEYS.md.
  D8 (user 2026-11-20) The status bar (D3) shows the mode, the current URL and messages
     (search counts `[3/17]`, "search hit BOTTOM, continuing at TOP", errors); COMMAND and
     SEARCH are typed in it. Other fields (load progress, hovered link target, pending `g`)
     are later items, only on request.
  PROPOSED (Claude 2026-11-20, not yet confirmed by the user; build the proposal unless
  the user says otherwise before the item starts):
  P2 In normal mode the page gets NO key events at all (keydown/keyup are not
     dispatched), so a page cannot cancel scratchy's keys. This reverses QJ11 ("a page may
     cancel any key, no reserved chord") for normal mode only; in input mode QJ11 stands.
  P3 The first Esc counts toward Esc Esc even when the page cancels it (preventDefault),
     otherwise vim.js-style pages that cancel Esc would lock the user out again (QJ11).
  P4 The one exception to D5's stickiness: clicking into a text control or select switches
     to input mode (you clearly want to type into the page). Mouse input always goes to the
     page in both modes.
  P5 Remove `:set vim`/`:set novim` (`App::vim_enabled`, `SET_ARGS` "vim"/"novim") and the
     SIGUSR1 bootstrap (`AppEvent::ToggleVimMode`, the signal-hook thread): with nothing
     but Esc Esc claimed in input mode, there's nothing left to turn off, and Esc Esc can't
     be locked out (P3). QCFG1's `vim` config key goes with them.
  P6 Input mode gets the UA default scroll keys every browser has when the page does not
     cancel them: ArrowUp/ArrowDown (line), PageUp/PageDown and Space/Shift-Space (page
     minus a bit), Home/End (already exist), only when no text control/select/media owns
     the key. Today only Home/End exist because j/k covered the rest.

QSEARCH — `/` search, n/N, Enter (user design session 2026-11-20; needs QKEYS2)
========================================================================

- QSEARCH-D DESIGN (user, 2026-11-20; state machine rows in KEYS.md, which wins on any
  conflict). Vim-style search in normal mode (QKEYS-D D7).
  S1 `/` in normal mode opens SEARCH: the query is typed in the status bar (same editor as
     `:`, TextEditBuffer). Enter commits and goes back to normal mode; the current match
     is the first one at or below the top of the screen in document order (none below:
     wrap to the first, with the wrap message) (user 2026-11-20, KEYS.md T23); Esc cancels (no change) and goes back to normal mode.
  S2 What is searched: the RENDERED text of the laid-out page (layout text runs), not DOM
     text, so hidden text never matches and every match has a position to scroll to and
     paint. A match may span inline element boundaries (`foo<b>bar</b>` finds "foobar"),
     not block boundaries. Plain text, SMARTCASE (case-insensitive unless the query has a
     capital). No regex. Only the top-level document (not iframes, not inside text controls).
  S3 Highlights are chrome painted over the page (like the scrollbar): every match one
     colour, the current match a stronger one. Esc in normal mode clears them (QKEYS-D D6);
     the query is kept. The status bar shows `[i/N]` and the wrap message (D8).
  S4 `n` / `N`: next / previous match in document order, wrapping with the status-bar
     message. Every move to a match (`n`, `N`, and the Enter that commits S1) brings the
     screen to it (user 2026-11-20): if the match is not fully visible the viewport
     scrolls so it is vertically centred (clamped at the page ends; like Firefox's find
     bar); if it is already fully visible nothing scrolls. A match inside a scrollable
     element scrolls that element too (innermost first, then the page).
  S5 Matches are recomputed after every relayout (live pages keep changing); the current
     match stays the nearest one to where it was.
  S6 Across navigations: the last query is kept (like vim's last-search register), the
     highlights are not: `n` on a new page runs the kept query there.
