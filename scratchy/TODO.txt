scratchy — known gaps / deferred work

Plain checklist of things found-and-deliberately-deferred during work on
this project, so they don't get forgotten between sessions. Not a
feature backlog of things nobody asked for — only things we actually
hit and chose not to fix immediately. See NOTES.md for the fuller story
behind any item; a commit hash in parens points at the commit it came
up during (`git show <hash>`) — more precise than a PROMPTS.md version
number, since several versions can share one commit and a hash is
directly actionable. PROMPTS.md is append-only and never edited for
these.

- [ ] `rem`, `%`, and unitless (besides literal `0`) are still not
      supported length forms (`px` and `em` landed — see PROMPTS.md
      v14). Not adding them until `default.css` or a real test page
      actually needs one — it currently doesn't use either anywhere.

- [ ] Table layout (PROMPTS.md v15) uses equal-width columns, not real
      CSS auto table layout (which sizes each column from the min/max
      content width of its cells). No colspan/rowspan (default.css/
      real-world markup don't need them for anything scratchy renders
      yet), no border-collapse/borders-between-cells (default.css
      doesn't declare any table/cell borders), no `caption-side`
      placement (caption always renders in source position, which is
      first — same as the default anyway). Revisit if a real page
      shows up with genuinely uneven column content that looks wrong
      under equal-width.

- [ ] `font-family` (PROMPTS.md v16) only recognizes the 5 CSS generic
      keywords (serif/sans-serif/monospace/cursive/fantasy) — no named
      families (`"Georgia"`, `Helvetica`, ...) and no comma-separated
      fallback lists. `default.css` only ever uses the bare `monospace`
      keyword, so nothing needs more than this yet.

- [ ] `text-decoration` (PROMPTS.md v17) only tracks the line keywords
      (underline/line-through/overline/none) — `text-decoration-style`
      keywords (`dotted`/`dashed`/`wavy`/`double`) and an explicit
      `text-decoration-color` are accepted in the value (so they don't
      make the whole declaration drop) but not tracked: every line
      scratchy draws is solid, in the text's own color. `abbr[title] {
      text-decoration: dotted underline }` in default.css currently
      renders as a plain solid underline, not dotted.

The rest of this file is a full html-rendering feature-gap survey done
after v20 (commit 7950fc2), not individual things hit mid-feature like
the items above — see the conversation that asked "what features are
missing in regards to rendering html?" Grouped by area so a future
session can pick a coherent slice rather than one property at a time.

- [ ] No positioning model at all: `float`/`clear`, `position`
      (relative/absolute/fixed/sticky), and `z-index`/stacking contexts
      are unparsed and unimplemented. Everything lays out in plain
      in-flow block/inline order; nothing can be taken out of flow or
      overlap deliberately.

- [ ] No flexbox (`display: flex`) or grid (`display: grid`) — `Display`
      only has Block/Inline/None/Table/TableRow/TableCell/TableGroup.
      `default.css` doesn't need either today, but most real-world pages
      do for their outer page chrome.

- [ ] A cluster of CSS properties are either unrecognized (dropped) or
      recognized-but-inert, none needed by `default.css` yet:
      `cursor`, `word-spacing`,
      `overflow`/clipping, and `font-weight: bolder`/`lighter` (only
      the literal `bold`/`normal` keywords are recognized — unlike
      `font-size: larger`/`smaller`, v29, nothing in `default.css`
      actually declares `bolder`/`lighter`, so there's no currently-
      inert rule this would newly activate; lower priority).
      (`line-height` landed in v24, `visibility` in v25, `outline` in
      v26, `box-shadow` in v27, `border-radius` in v28, relative
      `font-size` keywords in v29, `border-style` in v30 — all below
      now, not in this cluster. `letter-spacing` was attempted and
      reverted, `opacity` was scoped out — see their own items below,
      neither is a cluster member anymore.)

- [ ] `border-style` (PROMPTS.md v30) only distinguishes `dashed`/
      `dotted`/`double`/`none`/`hidden` from a plain solid stroke —
      `groove`/`ridge`/`inset`/`outset` all fall back to rendering as
      `solid`, since a real bevel effect needs two-tone shading this
      file's flat-fill painting primitives don't have (`hr`'s
      `border-style: inset` in `default.css` already rendered solid
      before this property existed at all, so this is a no-op for it,
      not a regression). Revisit if a real page's bevel border looks
      visibly wrong as flat solid instead.

- [ ] `border-radius` (PROMPTS.md v28) only rounds a plain background
      fill — combined with a visible border (`border-width > 0`),
      it's ignored entirely and both fall back to square corners. A
      correctly-rounded ring needs real per-pixel inner/outer-boundary
      testing; nothing in `default.css` or a real test page combines
      the two yet. Revisit if one does.

- [ ] **`opacity` was deliberately skipped, not attempted** — scoping
      it out surfaced a real design decision, not just an
      implementation task. Unlike every other paint-only property
      landed this session (`outline`/`box-shadow`/v12's
      `background-color`), `opacity` can't be resolved and applied
      purely within `resolve_style`/`paint`: real CSS opacity dims an
      element's *entire subtree* as one group (so a `<div
      style="opacity: 0.5">` with text inside dims the text too, not
      just the div's own background/border), which would mean
      threading a new accumulated-opacity parameter through all of
      `build_box_for_element`/`build_table_children`/
      `build_table_row_cells`/`build_children`/
      `build_children_with_prefix`/`collect_children` — a materially
      bigger, more invasive plumbing change than anything else done
      this run (every other ambient property so far only needed
      `collect_children` itself). Worse, a simplified "multiply each
      descendant's own alpha by an ambient accumulated opacity" isn't
      actually equivalent to real CSS opacity's group-compositing
      semantics — it'd visibly diverge for overlapping semi-transparent
      content (double-blending vs. single-group-composite), a
      correctness trade-off worth the user's input rather than a
      unilateral pick between that, a non-propagating
      own-element-only version (simpler but misleading — wouldn't dim
      a `<div opacity:0.5>`'s own text/children at all, surprising for
      the property's most common real use), or the invasive
      fully-correct plumbing.

- [ ] **`letter-spacing` was attempted and reverted (no commit) after
      finding what looks like a real cosmic-text 0.19.0 bug**, not a
      scratchy bug: `Attrs::letter_spacing()` is a real, documented
      API and wiring it in was mechanically straightforward (parsing,
      cascade, inheritance, `SpanStyle`/`shape_spans` threading — all
      implemented and headlessly verified correct in isolation, single
      span, no wrapping). The problem only showed up visually, on a
      real multi-word paragraph: cosmic-text's word-wrap line-breaking
      starts firing *far* too early once `letter-spacing` crosses a
      small threshold, shattering a paragraph that should easily fit
      on one line into one-word-per-line (worse: close to one-
      character-per-line at larger spacing values). Reproduced and
      measured in isolation (not an artifact of scratchy's own layout
      code): `"Wide letter spacing "` at 900px available width wraps
      to 1 line up to ~2px of spacing, 2 lines at 3-4px, 3 lines at
      5-7px, 4 lines at 8px — clearly the line-breaking pass is
      computing available width or word width wrong once
      `letter_spacing_opt` is set, even though the *final* rendered
      glyph x-advance (confirmed separately) correctly includes the
      spacing. This is squarely inside cosmic-text's shaping/layout
      internals (`src/shape.rs`/`src/layout.rs` in the vendored
      0.19.0 source), not something fixable from scratchy's call
      site. Needs either: confirming this against a newer cosmic-text
      release (not checked — no network access this session), finding
      an upstream issue/workaround, or accepting a documented
      limitation (e.g. only support small letter-spacing values, or
      disable wrapping whenever letter-spacing is set — both would be
      lossy enough to want explicit sign-off before shipping, which is
      why this was skipped rather than guessed at).

- [ ] `box-shadow` (PROMPTS.md v27) is deliberately narrower than the
      real property: no `inset` (rejected outright, not misrendered as
      an outer shadow), no blur (`blur-radius` is parsed so it doesn't
      drop the declaration, but discarded — every shadow is a
      hard-edged solid rect), no comma-separated multiple shadows
      (just the first/only one), and `color` is required (no
      `currentColor` fallback for an omitted color). Revisit if a real
      page's shadow looks visibly wrong without blur, or needs
      `currentColor`/multiple layered shadows.

- [ ] No CSS custom properties (`--foo: ...` / `var(--foo)`).

- [ ] No at-rules at all — `@media`, `@import`, `@font-face`,
      `@keyframes`, and transitions/animations are all skipped outright
      at the stylesheet-parsing stage (`TopLevelParser`'s `AtRule`
      parsing is a deliberate no-op). No responsive breakpoints, no
      animation of any kind.

- [ ] `OurSelectorImpl`'s `NonTSPseudoClass` is a stub empty enum, so
      any pseudo-class needing element *state* can't even parse:
      `:hover`, `:focus`, `:active`, `:link`/`:visited`. (There's no
      interactivity driving most of these yet anyway — see the next
      item — but `:link`/`:visited` could matter for `a` styling even
      without hover/focus.) Structural pseudo-classes built into the
      `selectors` crate itself (`:not()`, `:nth-child()`,
      `:first-child`, etc.) are a separate question nobody has actually
      verified either way yet.

- [ ] No forms/interactive widgets (`input`/`button`/`select`/
      `textarea` render as plain unstyled DOM nodes, not widgets), no
      replaced/embedded elements (`img`/`svg`/`canvas`/`video`/`audio`/
      `iframe`/`object`/`embed` have no special handling or box model —
      nothing to draw anyway with no networking), and no JavaScript
      (html5ever only parses the DOM; `<script>` contents are read and
      discarded, never executed). The only interactivity scratchy has
      at all is mouse-wheel scroll and window resize — no link
      navigation, no keyboard input, no text selection. Networking
      itself (fetching the page, images, fonts, external stylesheets)
      remains a deliberately separate, not-yet-started concern from
      rendering — see NOTES.md.
