scratchy — known gaps / deferred work

Plain checklist of things found-and-deliberately-deferred during work on
this project, so they don't get forgotten between sessions. Not a
feature backlog of things nobody asked for — only things we actually
hit and chose not to fix immediately. See NOTES.md for the fuller story
behind any item; a commit hash in parens points at the commit it came
up during (`git show <hash>`) — more precise than a PROMPTS.md version
number, since several versions can share one commit and a hash is
directly actionable. PROMPTS.md is append-only and never edited for
these.

========================================================================
QUEUE — ranked work order (reviewed 2026-11-12, re-planned 2026-11-14)
========================================================================

Work through this queue top to bottom; it overrides the order of
everything below it. Everything below the QUEUE is history and detail.
An item here that says "Detail:" points at the longer entry further
down by its title text. Search for that text, because line numbers in
this file go stale.

Rules for whoever implements an item:
- Take the first unchecked item. Don't reorder the queue and don't
  merge items. If an item turns out to be wrong or much bigger than its
  size suggests, stop and report back. Don't guess.
- Follow the per-item checklist in `AGENTS.md`.
- Code references are function and type names only. Find them with
  `grep -n 'fn <name>' src/lib.rs`, and never trust a line number.
- When an item is done, tick it here AND in its "Detail:" entry, with
  the commit hash. If you deliberately leave part of an item out, add a
  new, narrower `[ ]` item right below it in this QUEUE.
- Sizes: S = under ~200 changed lines, a single concept. M = several
  functions, new plumbing. L = split it into the listed sub-items and
  do them one at a time.

Evidence base: `SCRATCHY_CSS_DEBUG=1` runs plus raw-CSS selector and
at-rule counts on four pages the user actually reads: Wikipedia
(SoHo_Weekly_News), social.loupax.com/u/loupax, forums.gentoo.org and
google.com. Numbers like "(n=47)" in an item are ignored declarations or
dropped selectors summed across those pages. Caveats:
- The gentoo page is CSS-only. `snag` timed out mid-fetch twice (its own
  bug, not scratchy's), so the page body never arrived.
- The debug tool under-reports. It reports "no change" when a rule had
  already set the same value (Wikipedia writes every color twice,
  `color:#202122; color:var(--color-base,#202122)`). It never reports
  selectors or at-rules that were dropped wholesale. Q1 fixes both of
  those blind spots.
- Most of the sites the user browses require JavaScript, so they can't
  be measured yet. Re-run this measurement after Tier 1 lands, and
  re-rank if the numbers move.

- [x] Q2 [S] (66bdc60) Pseudo-classes that are dropped today (n=225 selectors on

      `to_css`) and to `match_non_ts_pseudo_class`:

        `:focus-within`, `:target`: never match.
      - `:checked`: matches an `input` that has the `checked` attribute,

      (that entry's test plan applies). Done when Wikipedia's "Jump to

- [x] Q7 [M] (407d3bf) CSS-wide keywords `inherit`, `initial`, `unset`, `revert`
      and `revert-layer` (n=70+: `color` 28+16, `vertical-align` 14,
      `background` 8, `font-size` 8, `line-height` 6, `display` 4).
      Nothing parses them today. Before dispatching to the per-property
      parsers, recognize these keywords in `parse_value` and record
      them per property. Semantics:
      - `unset`: same as `inherit` for an inherited property, and same
        as `initial` for a non-inherited one.
      - `revert` and `revert-layer`: treat as `unset`. There are no
        cascade layers or UA-origin split here.
      - `initial`: the property's initial value.
      - `inherit`: the parent's computed value.
      All of them must WIN the cascade at their own specificity; never
      treat them as "not declared". If doing every property is too
      invasive, scope to the properties listed above plus `font-family`,
      `font-weight`, `text-align`, `white-space`, `cursor` and
      `visibility`, and document the rest as a new QUEUE line.

- [x] Real CSS2.1 Appendix E stacking-context semantics (v56, bc3b696): the
      seven-layer bottom-to-top paint order
      (https://www.w3.org/TR/CSS21/zindex.html) is now genuinely modeled
      per stacking context — (1) this box's own background/border, (2)
      negative-`z-index` descendant stacking contexts, (3) in-flow
      non-positioned non-floated block descendants, (4) floats, (5)
      in-flow inline descendants, (6) `z-index: 0`/`auto` positioned
      descendants, (7) positive-`z-index` descendant stacking contexts —
      verified layer-by-layer with a permanent pixel test, not assumed.
      Two concrete fixes over the old, narrower model (every out-of-flow
      box used to paint in one flat ascending-`z-index` group, always
      *after* its containing block's own content, regardless of sign):

      Negative `z-index` now paints *above* its own containing/stacking-
      context box's own background/border but *below* that box's normal
      content (layer 2 sits between layers 1 and 3). Checked directly
      against the spec rather than assumed: the intuitive "negative
      z-index hides behind its own box's background" is a common but
      *inaccurate* paraphrase of the real rule — Appendix E lists
      background (layer 1) *before* negative stacking contexts (layer 2)
      in its bottommost-first order, meaning negative paints on top of
      it; it only looks "hidden behind everything" when the relevant box
      happens to have no background of its own, leaving nothing else for
      it to appear in front of.

      `position: relative`/`sticky` with an *explicit* `z-index` now
      establishes its own descendant stacking context (real CSS2
      §9.9.1) — pulled out of plain document-order painting to compete
      by `z-index` with its containing block's other out-of-flow
      descendants instead, the same way `absolute`/`fixed` already did.
      `z-index: auto` on `relative`/`sticky` is unaffected (still
      today's plain paint-position-only treatment — real CSS: `auto`
      does not establish a stacking context).

      The "two unrelated in-flow subtrees overlapping" generality the
      original item worried about turned out to be reachable, just not
      in the unbounded way the old wording implied: a `position:
      relative` box's own offset can already overlap a *sibling* in the
      same parent's `Blocks` list (float/clear, v54, only narrows
      content *around* a float — it doesn't let two unrelated block
      subtrees overlap arbitrarily anywhere on the page). Scoped to
      exactly that reachable case — sibling-level, same immediate parent
      — rather than building a fully general cross-subtree stacking
      search for a case that doesn't occur in this layout model.

      Deliberately scoped out, each documented precisely rather than
      silently dropped:
      - [ ] A `relative`/`sticky` box's own explicit-`z-index` stacking
            context is always anchored at its *immediate* containing
            block (the same box that already catches its own
            `absolute`/`fixed` descendants), never bubbled past an
            intervening ancestor that is itself positioned but has
            `z-index: auto` — real CSS would let such an ancestor's own
            descendants' `z-index` comparisons bubble further up past it
            (an auto-`z-index` positioned box doesn't establish its own
            context), which this doesn't model. Not reachable by
            anything `default.css` or a real test page needs yet (deep
            nested positioned-with-auto-`z-index` ancestors containing
            an explicitly-`z-index`ed descendant are uncommon), but a
            real, narrower gap than the general case this item used to
            describe.
      - [ ] `hit_test_cursor`'s negative-`z-index` priority doesn't fully
            mirror `paint`'s now-corrected order: a negative stacking

- [ ] **(Was top priority; its GET/link-click half has landed — what's
      left is blocked on forms, see QUEUE at the top of this file.)
      scratchy speaks HTTP
      over a unix socket — replaces talking to `snag --serve` directly,
      unifies link-click navigation and form submission under one
      transport.** Supersedes the old link-nav-specific socket protocol
      (v65) and the narrower, forms-only "just print the request"
      sketch this item previously held — both collapse into one
      mechanism now. Decided in conversation (see PROMPTS.md's own
      entry for the full reasoning trail, not repeated here):

      - **`snag`'s scope narrows to exactly one job, and it's done
        there**: bundle a page to a single self-contained file. It is
        *no longer* scratchy's live-navigation transport at all — v65's
        `fetch_from_snag`/`fetch_from_snag_at`/`snag_socket_path`
        (talking to `snag --serve`'s own `$XDG_RUNTIME_DIR/snag.sock`/
        `/tmp/snag-$UID.sock` auto-discovered line protocol) are
        replaced outright, not extended or kept as a fallback.
      - **A new, separate third tool, named `wire`** owns real
        networking from now on: it accepts a request over a unix
        socket, actually executes it (TLS, redirect-following,
        decompression — reusing `ureq`, the exact crate `snag` already
        trusts for this), and returns a normalized HTTP/1.1 response. No
        bundling/inlining logic of its own — that stays `snag`'s
        exclusive job; this tool is much smaller than `snag`. Lives in
        this same repo, alongside `scratchy`/`snag`, as its own crate —
        no shared-prefix naming scheme for now (the user's own call:
        revisit a `vibe-`-prefixed naming convention across all three
        tools only if this project ever picks up a second user).

        **The daemon itself is built (`wire/`, v1 — see its own
        `PROMPTS.md`/`NOTES.md`/`TODO.txt`)**: request parsing
        (absolute-form request line, headers, `Content-Length` body),
        real execution via `ureq` (TLS/redirects/gzip decompression),
        response normalization (a real 4xx/5xx from upstream forwards
        as itself, not a transport error; `Transfer-Encoding`/
        `Content-Encoding` are stripped and a fresh `Content-Length`
        is computed over the already-decoded body; a genuine transport
        failure — DNS/connect/TLS — synthesizes a `502` rather than
        hanging or crashing the connection), and the daemon's own
        `--socket`-overridable default-path/stale-socket-cleanup/
        concurrent-connections-via-one-thread-per-connection plumbing,
        all covered by 10 permanent tests (including one real Unix-
        socket round trip).

        **`scratchy`'s own side — the GET/link-click half — is also
        built now (v66)**: `fetch_from_snag`/`fetch_from_snag_at`/
        `snag_socket_path` are gone, replaced by `build_get_request_
        text`/`fetch_via_wire_at`/`parse_wire_response`/`dispatch_wire_
        response` (a real absolute-form request, real response-framing
        dispatch by `Content-Type`, a fetched image wrapped into a
        synthetic `<img src="data:...">` document rather than a second
        rendering mode), a new strict-opt-in `--socket <path>` CLI flag
        (no auto-discovered default), and the stdout-request-print
        fallback for "no socket configured or configured one
        unreachable." 8 new permanent tests. Live-verified further than
        any prior navigation work in this project: a real synthesized
        `xdotool` click, inside a real running `scratchy` process,
        against a real on-screen link, triggered real navigation through
        a real running `wire` daemon to a real local HTTP fixture — for
        both a fetched HTML page and a fetched image — confirmed via
        before/after screenshots (see `PROMPTS.md`'s own v66 entry).

        **A live-navigated page's own non-inlined sub-resources are
        also fetched now (v67)** — the gap `snag`'s own inlining always
        covered for a bundled page, but nothing did for one reached by
        clicking a link, since that path never goes through `snag` at
        all. `process_external_resources` (`start_navigation`'s own
        background thread, after the top-level page itself comes back)
        parses the fetched HTML into a throwaway DOM just long enough to
        find every `<link rel=stylesheet href>`/non-`data:` `<img src>`,
        resolved against the page's own `<base href>` (or its URL, if it
        has none). Stylesheets are fetched over `wire` *synchronously*,
        right there, and concatenated into `App::extra_css` — present

        document` clears it on every navigation) — so the page renders
        immediately and each image materializes as its own fetch lands,
        never blocking the rest of the page. `resolve_img` falls back to
        this cache for any `src` `decode_data_uri` doesn't recognize. 9
        new permanent tests (177 total, up from 168 — fetch/content-
        type-dispatch/DOM-scan/cache-lookup/cascade-merge functions each
        covered individually; the thin orchestration
        between them rests on code review + live verification, same
        category as `start_navigation`'s own click wiring already is).
        Live-verified past even v66's own bar: a real click through a
        real `wire` daemon to a real local HTTP server picked up a real
        external stylesheet (applied before first paint) and a real
        fetched image; a deliberately slow image route confirmed the

        the image appeared on its own with no further click — see
        `PROMPTS.md`'s own v67 entry for the full screenshot trail.

        **Still fully open**: `<button>`/form-element support doesn't
        exist at all yet (no box, no focus tracking, no keyboard
        handling — see the sequencing-plan item above), so form
        submission can't be wired to `wire` until that lands first;
        `snag` itself hasn't been narrowed yet (`--serve` is still
        there, unremoved, even though nothing calls it anymore —
        removing it is `snag`'s own change to make, not scratchy's, and
        is safe to do independently whenever `snag`'s own session picks
        it up); and sub-resource fetching only happens for a *live-
        navigated* page — `scratchy --socket <path> some-static-file.html`
        and `snag url | scratchy --socket <path>` never call `process_
        external_resources` at all, even with a socket configured, so a
        static/streamed page's own un-inlined references (if any — a
        `snag`-bundled one never has any to begin with) still won't
        resolve. Not attempted: nothing has needed it, and `App::new_
        static`/`new_streaming` would need their own trigger point for
        it, a genuinely separate piece of plumbing from `start_
        navigation`'s.
      - **Request framing**: a real HTTP/1.1 request, using the
        standard proxy "absolute-form" request line (`GET https://
        example.com/path HTTP/1.1`, RFC 7230 §5.3.2) rather than the
        origin-relative form a direct browser connection would send —
        this is what lets a daemon behind a bare unix socket (no DNS/
        TLS-SNI of its own to infer a destination from) know exactly
        where to actually connect, using only standard HTTP syntax, no
        invented command/framing layer on top.
      - **Response framing — the one point actually debated and
        resolved in conversation**: the daemon does *not* relay raw
        bytes 1:1 (that would leave chunked-decoding/redirect-looping/
        gzip-decoding as new HTTP-client logic inside scratchy, which
        contradicts "scratchy still doesn't do its own networking").
        It also doesn't try to collapse different content kinds into
        one shape — a fetched `index.html` and a fetched `photo.jpg`
        are genuinely different things scratchy must handle
        differently. The resolved contract: the daemon returns a clean,
        already-decoded HTTP/1.1 response — real headers, redirects
        already followed, body already decompressed, `Content-Length`
        never `Transfer-Encoding: chunked` — and scratchy reads exactly
        one header out of it to decide what the body *is*:
        `Content-Type`. `text/html` → the existing HTML-parse path
        (`new_parser().read_from(...)`, same as v65's `AppEvent::
        NavResult` success branch already uses). `image/png`/`jpeg`/
        `gif`/`webp` → the existing `decode_image_bytes` path (already
        built and tested for `data:` URI images — reusable verbatim on
        real fetched bytes, no new image-decoding code). Anything else,
        for now: a clear "can't render this content type" inline
        message, never an attempt to force unknown bytes through either
        path. Every other header (`Cache-Control`, `Server`, cookies,
        etc.) is read by nobody and simply discarded — confirmed with
        the user directly: normalizing the *transport* mess is the
        daemon's job, but deciding what the bytes mean stays scratchy's.
      - **One connection per request on the scratchy↔daemon leg, no
        multiplexing there — but concurrent *separate* connections are
        expected, not excluded.** Same dead-simple shape `snag --serve`'s
        own protocol already has: connect, write the request, read
        until the daemon closes, done, no request IDs or shared-
        connection framing. Discussed and settled in conversation: real
        multiplexing (interleaving several requests' bytes over one
        shared connection) would need both sides to agree on framing —
        it can't be hidden in the daemon alone, since scratchy is the
        other half of that exchange and would need new ID-tagging/demux
        code regardless of how smart the daemon is — and it would buy
        nothing here anyway, since a unix socket is local IPC with no
        handshake; opening several concurrent one-shot connections
        (future per-resource fetches firing off N background threads,
        the same shape `start_navigation`'s background thread already
        uses, just invoked more than once at a time) costs about as much
        as opening one. The real place for connection pooling/reuse is
        the *daemon's own upstream leg*, talking to real remote servers
        over actual TCP/TLS — the daemon is free to reuse/pool its own
        connections to the same remote host across multiple client
        requests however it likes, entirely invisible to scratchy, with
        zero protocol impact on the scratchy-facing socket. That's where
        the real performance cost (handshakes, round trips to a real
        server) actually lives, and it's already implied by "the daemon
        owns networking" — nothing new to design there, just a reminder
        not to conflate the two legs.
      - **`--socket <path>` becomes an explicit opt-in CLI flag**,
        replacing today's fixed-path auto-discovery entirely. No flag
        given, or any connection failure against the given path: falls
        all the way through to printing the raw request text to stdout
        (the literal HTTP/1.1 wire text — request line, `Host`, other
        headers, blank line, body — chosen specifically so it's directly
        replayable by `nc`/a raw socket/this same new daemon run
        manually, with zero translation) plus the existing inline
        "not available" status-message precedent (v65's connection-
        refused handling) — scratchy never gets a response back in this
        branch, by design; that's the whole point of the fallback.
      - **Forms and link-clicks become the exact same code path**: both
        reduce to "build a request (GET for a link or a `method=get`
        form, GET/POST for a form depending on its own `method`
        attribute), try the socket, else print" — resolving the
        asymmetry this conversation flagged earlier (link-nav always
        navigated live, forms always only printed; now both depend
        purely on whether `--socket` is active and reachable, not on
        which kind of control was clicked). Form value-collection itself
        (walk to the nearest ancestor `form` via the existing
        `parent_handle`/`El` machinery; read `value`/
        `checked`/selected-`<option>`/textarea-text from the live DOM
        per control type; encode via `url::form_urlencoded`, already a
        dependency; resolve `action` against `base_url` via the existing
        `resolve_href`) is unchanged from this item's
        earlier draft — only the transport underneath it changed.
      - **Click-side rewrite this item actually requires**:
        `build_box_for_element` needs the same early-
        return shape it already gives `img` (via
        `build_img_box`) for `<button>`/`input[type=submit]`, with
        a new `submit_handle: Option<Handle>` field on `LayoutBox`
        (`None` at its ~9 other construction sites) so
        `hit_test_cursor` (already a 2-tuple with `href` —
        widens to a 3-tuple, same shape v65's own `href` addition used)
        can report back *which* element was clicked. `start_navigation`
        and the `WindowEvent::MouseInput` handler both get rebuilt around the new socket protocol
        and request-building rather than the old bare-URL-line one.
      - **Still just a transport, not a solution to async resource
        loading**: this unblocks future `<img src="https://…">` fetches
        (same daemon, same request/response shape, same Content-Type
        dispatch) but doesn't by itself implement them — that still
        needs the separate, not-yet-built per-resource cache/placeholder/

        Rc<DecodedImage>>` on `App`, same shape `scroll_offsets`

        background thread + send an `AppEvent` back into the winit

        function testable with no `App`/winit involved (parse a fixture

      older `:hover`/`:focus`/`:active` item above. Today
      `OurPseudoClass` only knows `:link`/`:visited`/`:root`, so any
      selector mentioning `:focus` fails to parse and **the whole rule
      is dropped**, including `:not(:focus)` rules that should *match*
      on a page with nothing focused. Real hit: Wikipedia's
      `.mw-jump-link:not(:focus){display:block;position:absolute
      !important;clip:rect(1px,1px,1px,1px);width:1px;height:1px;
      margin:-1px;overflow:hidden;...}` is dropped, so "Jump to content"
      renders as a visible in-flow line at the top of every Wikipedia
      page instead of being taken out of flow as a 1x1 box. Fix: add
      variants for these to `OurPseudoClass` (parse + `to_css`), and
      have `match_non_ts_pseudo_class` return `false` for them. That is
      exactly true for a browser with no focus/hover state, and it makes
      `:not(:focus)` correctly match everything. Leave real state
      tracking to the older item. Test: a `:not(:focus)` rule applies
      and a plain `:hover` rule doesn't, and neither breaks parsing of
      the other selectors in the same comma-separated list (check how
      selector-list parse failure currently behaves first; a list with
      one bad selector drops the whole rule per spec, which is another
      reason to stop rejecting these). Note: `clip:` is not supported,
      but `width/height:1px` + `overflow:hidden` + `position:absolute`
      should already hide the text in practice. Verify by rendering.
