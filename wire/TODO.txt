wire — known gaps / deferred work

Same spirit as scratchy/TODO.txt and snag/TODO.txt: things found-and-
deliberately-deferred, not a speculative feature backlog. See NOTES.md
for the fuller story behind any item; a commit hash in parens points at
the commit it came up during.

- [x] **`scratchy` talks to `wire` now** (`scratchy` v66/v67, a separate
      session — see `scratchy/PROMPTS.md`). Link-click navigation and
      a live-navigated page's own sub-resources (external stylesheets,
      non-inlined images) both go through `wire`; `fetch_from_snag`/
      `fetch_from_snag_at`/`snag_socket_path` are gone from `scratchy`
      entirely. Still open, on `snag`'s own side: `snag --serve` itself
      hasn't been removed, even though nothing calls it anymore —
      `snag`'s own change to make, not this crate's.

- [x] (2026-11-17: scratchy Q30e, f164a2b, now submits GET and POST forms through
      wire; the text below is the original note) **Form submission has no transport yet.** `scratchy` has no
      `<button>`/focus/keyboard subsystem at all (see its own
      `TODO.txt`'s "Form elements — sequencing plan" item), so nothing
      can drive a POST through `wire` yet even though the daemon itself
      already supports a request body. Not a gap in `wire` — blocked
      entirely on `scratchy`'s own, unrelated, not-yet-started work.

- [ ] **Not live-verified against a real public Internet host.** This
      sandbox's own outbound network policy denies `CONNECT` to
      arbitrary hosts (confirmed directly with `curl`, independent of
      this code entirely — see PROMPTS.md v1's live-verification
      section for the full trail), so the real "fetch `https://
      example.com/` through a running `wire`" path has only been
      exercised against local loopback fixtures (real TCP, real HTTP
      framing, just not the real Internet) — not a literal end-to-end
      check against a real remote server. Worth doing for real the next
      time a session's sandbox allows it.

- [ ] **`brotli` decompression isn't supported**, only `gzip` (`ureq`'s
      `gzip` Cargo feature) — a response with `Content-Encoding: br`
      would be forwarded still-compressed with its `Content-Encoding`
      header stripped (since `normalize_response` always strips it,
      regardless of whether it could actually decompress the body),
      which would hand scratchy raw brotli bytes it has no way to know
      are still encoded. `gzip` is the dominant real-world encoding by a
      wide margin and nothing real has hit a brotli-only server yet —
      revisit if one does.

- [x] (DONE in scratchy QF6: `X-Wire-Timeout-Ms` per request, with `X-Wire-Max-Bytes`/
      `-Max-Redirects`/`-Policy`; the text below is the original note) **No request timeout tuning, no per-request override** — every
      request shares one fixed 20s agent-level timeout (same default
      `snag`'s own `build_agent` already uses), with no way for a
      particular request (e.g. a user explicitly waiting on a known-slow
      endpoint) to ask for longer or shorter. Hasn't mattered yet — only
      one real client exists, and it has no concept of per-request
      timeout preferences either.

- [ ] **Cookie control channel has no access token** (user decision 2026-11-17:
      no token for now). The cookie-jar control requests (`X-Wire-Cookie-Op`,
      clear/read of the jar) are open to any process that can reach `wire.sock`,
      which sits under `/run/user/<uid>/` so in practice only the same user.
      Hardening idea: a random token wire writes to a file readable only by the
      user, required on the control channel, read by scratchy at startup (adds a
      startup dependency between the two). Firefox has no equivalent: its jar
      sits behind a private IPC channel. Do this only if the user asks.

- [x] (DONE 2026-11-21, scratchy QSTASH5) **W-PERSIST1: `--cookie-file PATH`** (scratchy QSTASH5; design in
      ../scratchy/STASH.md "Cookies (wire)", user 2026-11-19). Load the jar at
      start; save it (temp file + rename, mode 0600) at most once a second while
      it has changes, and on SIGTERM. Cookies with no expiry date are not saved.
      Format is wire's own (one cookie per line). Plus a control op
      `X-Wire-Cookie-Op: clear-site` with `X-Wire-Top-Site`, for scratchy's
      forget-site, advertised in `X-Wire-Features` (e.g. `jarfile`). Without the
      flag: today's in-memory jar. Tests: round trip through a temp file,
      session cookies dropped, expired cookies dropped on load, clear-site
      removes only that partition. With cookies on disk the missing control
      token (item above) matters more: ask the user before shipping.

- [x] (DONE 2026-11-17, QY39a, hash 27ce684: X-Wire-User-Agent / own User-Agent, X-Wire-Features: ua) **User-Agent override from scratchy** (user decision 2026-11-17; scratchy/TODO.txt
      QY39a/QY39b). wire sends a fixed honest UA
      (`wire/0.1 (+https://github.com/Loupax/vibe-it ...)`), which YouTube classifies as a
      bot (ES5 + polyfills variant). Let scratchy override it per request (an
      `X-Wire-User-Agent` request header, or the request's own `User-Agent`), keep the
      default when absent, document it in README.md, never forward other `X-Wire-*`
      headers upstream. Pair with scratchy's `--user-agent` flag (QY39b).

- [ ] **No TLS certificate pinning/custom root-CA support** — `ureq`'s
      own default TLS config (via `rustls`, the default backend) is
      used as-is. A real need for this would most likely surface as "a
      real site's cert fails to validate for a reason that isn't the
      site's own fault" — nothing like that has come up.

- [x] (MEASURED 2026-11-17, scratchy QM1d / REGRESSIONS.md R30: reuse is real.
      Ten ranged GETs to one loopback server through the running wire all
      arrived from the SAME upstream client port, one port for the shared agent
      and one for `manual_agent` (the jar path); a pooled connection was still
      reused after 65 s idle. Side effect found: W-POOL1 below.)
      **No connection reuse/pooling across requests to the same remote
      host** — `ureq::Agent` does do its own internal connection pooling
      per `Agent` instance already (confirmed by its own docs), and
      `wire` uses exactly one shared, cloned `Agent` across every
      connection/thread, so this may already be getting real reuse for
      free with zero extra code here — not independently confirmed with
      a direct measurement (e.g. counting actual new TCP handshakes
      across two requests to the same host), so flagged rather than
      assumed. `scratchy/TODO.txt`'s own design conversation explicitly
      called this out as the daemon's own business, invisible to
      scratchy either way — worth a real measurement before relying on
      it, not before using it.

- [ ] **Duplicate request headers collapse to one.** `execute` calls
      `req.set(name, value)` per parsed header, which *replaces* any
      prior value for that name rather than appending a second value —
      correct for the overwhelmingly common case (each header name
      appears once), wrong for a request that deliberately repeats one
      (e.g. multiple `Cookie` headers, rare but legal). Nothing real has
      sent one of these yet.

- [x] `file://` URLs are served (scratchy Q22). Open: no directory listings, no HEAD.

- [x] **W-POOL1 [S, security] `X-Wire-Policy: public-only` and `X-Wire-Target-Class`
      are skipped on a pooled connection** (found by scratchy QM1d, REGRESSIONS.md
      R30, 2026-11-17). Both come from `TrackingResolver`, which only runs when ureq
      opens a NEW connection. When the agent reuses a pooled one, nothing resolves:
      measured against the running wire with a loopback server, `public-only` to
      `http://localhost:<port>/` answered `403 policy` on a cold pool, then, after one
      plain request to the same host:port, the SAME `public-only` request answered
      `206` with no `X-Wire-Target-Class` / `X-Wire-Hop-Classes` (also on the jar
      path's `manual_agent`, and for every plain repeat request). Impact: scratchy
      sends `public-only` only with `private_targets = Block` (not the default), so
      the default Warn mode just loses the "DNS name resolved to a private address"
      warning on repeat requests; in Block mode a page-JS request to a private host
      gets through whenever an earlier request without the header (a sub-resource,
      an `<img>`, a media range read) pooled a connection to that host:port.
      Fix options: (a) remember the class per pooled (scheme, host, port) when the
      resolver runs and look it up on reuse (a map in `Shared`, filled by the
      resolver; entries live as long as ureq's pool may keep the socket), or (b) use
      a separate agent (own pool) for `public-only` requests so they always connect
      through the checking resolver, and report the class from the map in (a).
      (b) alone is the smallest secure fix; (a) also fixes the missing headers.
      Tests: unit test with a loopback fixture: plain request, then `public-only` to
      the same host:port -> 403 `policy`; two plain requests -> both carry
      `X-Wire-Target-Class: loopback`. Acceptance: the two-step sequence above
      against a rebuilt wire answers 403 on the second step.
      DONE (ca5e6c7): separate public-only pools + CLASS_MAP; see NOTES.md.

- [ ] **W-MEDIA1 [S] `file:` URLs: honour `Range` and name media types** (scratchy
      QM1e needs it for local `<video src=clip.mp4>` pages and fixtures; R30).
      Today `serve_file` reads the WHOLE file into memory (`std::fs::read`) and
      answers `200` with no `Accept-Ranges`, ignoring `Range` (measured: a 64 MiB
      file came back whole for `Range: bytes=0-1023`), and `.mp4/.webm/.ogg/.mp3/
      .m4a/.opus/.wav` are `application/octet-stream`. Do: parse one
      `bytes=a-b` / `bytes=a-` / `bytes=-n` range, answer `206` +
      `Content-Range: bytes a-b/total` + `Accept-Ranges: bytes` reading only that
      slice (seek + read_exact), `416` + `Content-Range: bytes */total` when out of
      range, `Accept-Ranges: bytes` on plain `200`; stream large files instead of
      `std::fs::read`; add the media types (video/mp4, video/webm, audio/ogg,
      audio/mpeg, audio/mp4, audio/opus, audio/wav). Multi-range requests: answer
      the full `200` (allowed by RFC 9110). Not a protocol change (HTTP semantics).
      Tests: a temp file: `bytes=0-9`, `bytes=5-`, `bytes=-3`, past-end 416, no
      Range -> 200 with Accept-Ranges; memory: a 64 MiB file with `bytes=0-1023`
      returns 1024 bytes.

- [ ] **W-MEDIA2 [S] A truncated body is indistinguishable from a complete one.**
      `copy_body` returns `Ok` on an upstream read error, and the
      `X-Wire-Max-Bytes` path ignores `read_to_end`'s error (`let _ =`); since wire
      strips `Content-Length`, the client cannot tell a dropped upstream (or the
      ureq total timeout, which INCLUDES reading the body: 20 s default) from the
      real end. For ranged media reads the client can compare with `Content-Range`
      (QM1e must), but other large bodies cannot. Option: when upstream sent a
      `Content-Length` (and no compression was undone), pass it on as
      `X-Wire-Upstream-Length: N` (protocol version 4); or, on the buffered
      `X-Wire-Max-Bytes` path, which knows the whole body before writing headers,
      answer `502` + `X-Wire-Error: truncated` instead of a short 2xx. Tests: a
      fixture that announces 1000 bytes, sends 10 and closes. Low priority: nothing
      has hit it yet.

- [ ] **W-PERF1 [S, optional] Streaming copy is the throughput limit through wire.**
      Measured (R30, loopback Python server, Python client): 4 MiB ranged GETs
      ~60-90 MB/s through wire vs ~145-200 MB/s direct; 1-byte ranges ~9 ms vs
      ~4-6 ms direct (about 5 ms of wire overhead per request: Unix accept, thread
      spawn, one unbuffered `write!` per header line). Video needs ~1-4 MB/s, so
      nothing needs this; if it ever matters: a 64 KiB `copy_body` buffer and a
      `BufWriter` around the header writes. Measure before and after.
